# Formal Verification & Advanced Testing for Solana/Anchor Programs (2026) — for Warden Wallet

## Findings

**Formal verification — Certora Solana Prover**
- Certora ported its Prover to Solana; Solana-specific specs are written in **CVLR** (Certora Verification Language for Rust), a Rust-embedded DSL distinct from EVM's CVL — `certoraRun` no longer targets Solana, dedicated Solana commands are used instead. [docs.certora.com/solana](https://docs.certora.com/en/latest/docs/solana/index.html), [CVLR spec](https://docs.certora.com/en/latest/docs/solana/speclanguage.html)
- **Squads v4** was the first Solana program formally verified by Certora (engagement Aug 29–Oct 5, 2023, "no major security flaws" found after "exploratory + rule-writing + hands-on testing"); Certora returned Dec 2024/Jan 2025 for further verification work on Squads. This was explicitly Certora's *first* Solana engagement — i.e., the toolchain was new even for a flagship user. [squads.xyz blog](https://squads.xyz/blog/certora-formal-verification-squads-protocol-v4), [certora.com/blog/sol-formal-verification](https://www.certora.com/blog/sol-formal-verification)
- Invariants require two proof obligations: init-establishes-invariant, and every method preserves it — a good structural match for account-state invariants like Warden's bucket/cap arithmetic. [docs.certora.com/cvl/invariants](https://docs.certora.com/en/latest/docs/cvl/invariants.html)
- **Cost**: commercial pricing is per-verification-minute (compute-time billed); free for open-source/academic projects. Warden is public on GitHub, which likely qualifies it for the OSS tier — worth confirming directly with Certora. [docs.certora.com/cvl/rules](https://docs.certora.com/en/latest/docs/cvl/rules.html)
- Prover is open-source itself: [github.com/Certora/CertoraProver](https://github.com/Certora/CertoraProver); curated Solana FV resource list: [alexzoid-eth/fv-resources](https://github.com/alexzoid-eth/fv-resources)

**Kani model checking (bounded, on Rust source)**
- OtterSec built a Kani-based prototype (2023) that integrates with `anchor-lang`: macro annotations (`#[succeeds_if]`, `#[errors_if]`, `#[invariant]`) on program code auto-generate CBMC proof harnesses. Applied to the **Squads multisig program** to prove account invariants (member-count bounds, `threshold ≥ 1`, `threshold ≤ members`) and instruction pre/postconditions. [osec.io/blog: Solana Formal Verification: A Case Study](https://osec.io/blog/2023-01-26-formally-verifying-solana-programs/)
- Explicit, stated limitations: **path explosion** on larger programs, CPI verification is "difficult if not impossible," and it "won't catch 100% of bugs" — described as a **prototype**, "mostly working" as of Jan 2023. No confirmed evidence this graduated to a maintained public tool since; treat as **UNVERIFIED / experimental** for 2026 production use without re-checking current state.
- Kani itself is a mature, AWS-backed, general Rust verifier (CBMC-backed bounded model checker), actively used to verify parts of the Rust standard library. [model-checking.github.io/kani](https://model-checking.github.io/kani/), [ArXiv Kani paper](https://arxiv.org/abs/2607.01504)

**Fuzzing — Trident (Ackee Blockchain)**
- Production-ready (current release ~0.11.x), MIT-licensed, `cargo install trident-cli`, Solana Foundation grant-funded. Historically honggfuzz-backed; newer versions describe a **TridentSVM client** (Anza's SVM API) as the execution backend, claiming up to ~12,000 tx/s. Anchor-like macros for writing fuzz harnesses; "manually guided fuzzing" (MGF) lets you steer generation toward tricky state transitions rather than pure random mutation. Explicitly used to secure **Kamino**. [github.com/Ackee-Blockchain/trident](https://github.com/Ackee-Blockchain/trident), [ackee.xyz/trident/docs](https://ackee.xyz/trident/docs/0.7.0/), [Introducing Trident](https://ackee.xyz/blog/introducing-trident-the-first-open-source-fuzzer-for-solana-programs/)
- Ackee also published a distinct pattern: **state-machine testing** for Solana programs (reference-model-vs-SUT transition comparison), independent of raw fuzzing. [ackee.xyz: State Machine Testing on Solana](https://ackee.xyz/blog/state-machine-testing-on-solana-blockchain/)

**Symbolic execution**
- **SseRex** (2026 research, arXiv) is described as the first *practical* symbolic executor operating directly on Solana bytecode/Anchor specs; large-scale run found 374 missing owner/signer checks and 100 arbitrary-CPI bugs across scanned programs. This is a **research tool**, not (as far as found) a packaged CLI teams install — treat as UNVERIFIED for hands-on availability. [arXiv:2603.16349](https://arxiv.org/pdf/2603.16349)

**Test harnesses: LiteSVM / Mollusk**
- **LiteSVM**: in-process SVM for fast unit tests (no validator). **Mollusk**: even lighter instruction-level harness (skips AccountsDB/Bank) for isolated CU/behavior checks. Solana's own recommended pyramid (2026): LiteSVM for fast unit tests → Mollusk for isolated instruction checks → Surfpool for integration realism. Both shipped fresh releases in July 2026 (LiteSVM v0.14.0, Mollusk v4.2.0-beta.0/v0.14.0), i.e., actively maintained. [solana.com/docs/programs/testing/mollusk](https://solana.com/docs/programs/testing/mollusk), [github.com/anza-xyz/mollusk](https://github.com/anza-xyz/mollusk), [Solana Changelog Jul 16 2026](https://solana.com/news/solana-changelog-july-16-2026)
- **proptest state-machine testing** (the `proptest-state-machine` crate, `ReferenceStateMachine` trait) is a generic Rust pattern — not Solana-specific — for driving randomized transition sequences against a reference model and comparing to the SUT; directly composable with LiteSVM/Mollusk as the SUT executor. [proptest-rs docs](https://proptest-rs.github.io/proptest/proptest/state-machine.html), [tzemanovic writeup](https://tzemanovic.gitlab.io/posts/state-machine-testing-with-proptest/)

**Verified/reproducible builds**
- `solana-verify` (Ellipsis Labs, now under `solana-foundation`) does deterministic Docker builds and hash-compares against the on-chain program; results surface in Solana Explorer, SolanaFM, Solscan via OtterSec's verified-programs API. This is **build-integrity**, not correctness verification — proves deployed bytecode matches public source, nothing about program logic. Known attack surface exists: Accretion published "How We Hacked Solana Verified Builds," so treat the pipeline itself as security-relevant, not just cosmetic. [solana.com/docs/programs/verified-builds](https://solana.com/docs/programs/verified-builds), [github.com/solana-foundation/solana-verifiable-build](https://github.com/solana-foundation/solana-verifiable-build), [Accretion: How We Hacked Solana Verified Builds](https://accretion.xyz/blog/verified-builds)

**Mutation testing**
- `cargo-mutants` is a mature, general Rust mutation tester (source-mutate-and-rerun-tests loop, flags code your tests don't actually assert on). No Solana/Anchor-specific integration found or needed — it operates at the `cargo test` level, so it works unmodified against Warden's existing LiteSVM Rust test suite. [mutants.rs](https://mutants.rs/), [github.com/sourcefrog/cargo-mutants](https://github.com/sourcefrog/cargo-mutants)

**Differential testing**
- The clearest Solana precedent is the Solana Foundation's Lean-based sBPF spec work: a "spinoza" harness differentially tests a Lean interpreter against the executable sBPF VM. This validates that a *formal spec* and the *real VM* agree — the same pattern Warden should apply one level up (reference bucket/cap accounting model vs. on-chain program). [github.com/solana-foundation/leanprover-solanalib](https://github.com/solana-foundation/leanprover-solanalib)

**Warden's current state** (per repo read): `programs/warden/` Anchor program, zero-copy `SmartAccount`/`SessionKey`, 292 Rust + 50 TS tests, all on **LiteSVM**, plus per-instruction serialized-tx-size assertions against the 1,232-byte limit. No Mollusk, no proptest, no fuzzing, no formal verification, no CI config found in the fetched content — UNVERIFIED whether CI exists elsewhere (repo listing was via a single fetch, not exhaustive).

## What Warden should adopt / change

1. **Add `cargo-mutants` now — cheapest, fastest ROI.** Run it against `programs/warden/` today; it needs zero new test infrastructure and will immediately surface assertions that pass despite dead/wrong logic — especially valuable for the bucket day/30-day rollover math and cap-comparison operators, which are exactly the off-by-one/boundary bugs mutation testing excels at catching. Gate CI on a mutation-score floor, not just line coverage.
2. **Introduce `proptest-state-machine` over the existing LiteSVM harness.** Build a `ReferenceStateMachine` that models SmartAccount/SessionKey/bucket state purely in Rust (no SVM), generate random instruction sequences (grant/revoke session, transfers at boundary amounts, day/30-day bucket resets, freeze/unfreeze, execute-with-CPI), and assert the reference model's post-state matches what LiteSVM produces after replaying the same sequence on-chain-style. This is the single highest-leverage addition: it directly targets Warden's stated risk surface (bucket accounting, cap enforcement, conservation checks) and reuses the existing LiteSVM harness as the SUT executor rather than requiring new infra.
3. **Adopt Trident for coverage-guided fuzzing**, layered on top of (2), not replacing it: property-based state-machine testing finds logic divergences under *structured* sequences you design; fuzzing finds crashes/panics/overflow/serialization edge cases under *adversarial* byte-level inputs (malformed WebAuthn `clientDataJSON`, malformed instruction data hitting the (program, discriminator) adapter registry, nonce-replay edge cases). Given Warden parses attacker-controlled WebAuthn JSON and rewrites arbitrary dApp transactions, this is a strong match for Trident's stateful, manually-guided mode — start Trident harnesses on `root_verify` (clientDataJSON scanner) and `execute` (adapter dispatch + conservation checks) first, since those are the two instructions parsing the most untrusted structure.
4. **Pursue Certora Solana Prover for the account-invariant core, once (2) has stabilized the reference model** — the reference state machine built in step 2 is nearly a spec-in-Rust already, which lowers the cost of writing CVLR rules. Target invariants: bucket totals never negative, session spend never exceeds min(per-tx cap, lifetime cap, bucket remainder), `execute`'s before/after conservation check is sound (no value creation/destruction across adapter-dispatched CPIs), and nonce is consumed exactly once. Check OSS-tier eligibility given the public repo before assuming cost is prohibitive; budget real calendar time — Squads' first engagement ran ~5 weeks even for an already-mature program.
5. **Treat Kani and SseRex as watch-list, not adopt-now.** OtterSec's Kani/anchor-lang prototype is explicitly unfinished (2023, "mostly working," CPI verification "difficult if not impossible") and no evidence of it becoming a maintained public tool was found — re-check its current repo state before investing. SseRex is a 2026 research paper with no confirmed packaged tooling. Both are worth a re-scan in 3–6 months, not a Q3 2026 commitment.
6. **Wire `solana-verify` into the deploy pipeline as a release gate**, not a verification technique — it proves deployed bytecode matches audited source, closing the "audit reviewed X, mainnet runs Y" gap. Given Accretion's writeup on defeating the pipeline, don't treat a green "verified" badge as a substitute for the above testing layers.
7. **Add Mollusk for CU-budget and instruction-isolation regression tests** alongside LiteSVM (LiteSVM for end-to-end multi-instruction flows, Mollusk for fast single-instruction CU/behavior snapshots) — this is Solana's own documented pyramid and is low-cost to add given LiteSVM is already in place.
8. **Spec-to-test traceability**: since no formal spec-linkage practice was found as an established Solana convention (this looks like a gap even at mature shops), Warden should self-impose one — tag each invariant in the proptest reference model and each CVLR rule with a stable ID, and reference that ID in a `docs/program/invariants.md` ledger alongside the existing `docs/program/` cost/error docs, so audit findings, mutation-testing gaps, and Codex review comments can all cite the same invariant IDs.
