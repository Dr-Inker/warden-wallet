# Passkey/WebAuthn/secp256r1 on Solana in Practice — Research Report

## Findings

**SIMD-0075 precompile is minimal by design.** The `Secp256r1SigVerify1111111111111111111111111` precompile (activated mainnet June 2025) only does raw ECDSA-P256 verification over instruction-referenced (sig, 33-byte compressed pubkey, message) triples, up to 8 sigs/ix; it enforces **low-S** strictly (high-S signatures fail outright) and rejects malformed offsets. It says nothing about WebAuthn — rpIdHash, clientDataJSON, flags, and nonces are entirely the calling program's problem. [SIMD-0075](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0075-precompile-for-secp256r1-sigverify.md), [Solana Compass changelog](https://solanacompass.com/learn/Changelog/solana-changelog-jul-24-epochrewards-agave-v20-release-schedule-solana-godot-sdk).

**LazorKit v2 (`lazor-kit/program-v2`, live source, fetched 2026-08-18) is the closest apples-to-apples comparator** — an Anchor-adjacent Pinocchio program doing exactly what Warden does: on-chain WebAuthn verification via the precompile + Instructions-sysvar introspection. Concretely:
- **clientDataJSON parsing**: a hand-written top-level-only JSON scanner (`extract_top_level_string_field`, `program/src/auth/secp256r1/webauthn.rs`) that walks brace depth, refuses any escaped (`\`) byte in keys/values (anti-injection), and — per an in-code regression comment ("M1") — was patched after a bug where a `}` inside a nested string value (e.g. `"tokenBinding":{"id":"x}y"}`) corrupted depth tracking and let the parser mis-locate `challenge`. This is direct evidence a naive brace-counting scanner is exploitable if string bodies aren't fully consumed — the exact class of bug Warden's "strict scanner" needs to guard against too.
- **rpIdHash handling**: computed once at authority *creation* and stored on-chain (145-byte fixed authority layout: header(48) + credential_id_hash(32) + pubkey(33) + rpIdHash(32)); every subsequent auth just byte-compares the authenticatorData's rpIdHash against the stored value — no origin string is ever checked. The code explicitly documents this choice: *"we intentionally do NOT validate the origin field... the binding that matters is rpIdHash, which the authenticator hardware/OS computes... and refuses to sign cross-origin."*
- **UV/UP**: only **User Present (UP)** is enforced (`is_user_present()` → reject if unset); **User Verified (UV)** is parsed (`is_user_verified()` exists) but is **not called anywhere in the authenticate() path** — i.e., biometric/PIN verification is not mandatory, only "a button was tapped." This is a materially weaker bar than Warden's UV-mandatory posture.
- **WebAuthn signature counter**: explicitly ignored — comment states synced passkeys (iCloud/Google) return 0 or non-monotonic counters, so it can't be used for clone-detection.
- **Replay protection**: a program-maintained `u32` odometer per authority (`header.counter`), client must submit exactly `counter+1`, **plus** a slot-freshness window (`MAX_SLOT_AGE = 150` slots, ~60s) checked against `Clock`. (An earlier public description of LazorKit — surfaced in secondary sources — describes a *SlotHashes-only* "proof of liveness" nonce scheme; the current v2 source shows this was superseded by the counter+slot-window design, so treat the SlotHashes-only claim as **UNVERIFIED for current code**, possibly describing v1.)
- **Precompile message binding**: offsets are locked to `0xFFFF` (current-instruction-only) for sig/pubkey/message and to fixed byte offsets — rejecting any attempt to point at a different instruction (cross-instruction substitution), and the precompile's message area is checked byte-for-byte against `authenticatorData ∥ SHA256(clientDataJSON)`. Anti-CPI: `get_stack_height() > 1` is rejected outright.
- **Multi-device/recovery**: authorities are modeled as a set with roles (`AddAuthorityArgs`: authority_type Ed25519/Secp256r1, role Owner/Admin/Spender) via `manage_authority.rs` — i.e., add-a-new-passkey-as-a-new-authority rather than rotate-in-place; no on-chain social/guardian recovery is evident in this file set (loss of all authorities = bricked, standard for this pattern). [github.com/lazor-kit/program-v2](https://github.com/lazor-kit/program-v2), files fetched 2026-08-18 raw from `main`.

**Squads Fuse/Smart Account Program**: OtterSec-audited and Certora-formally-verified for the core multisig/policy engine, but as of this research **passkey support is still not documented as shipped** — Squads' own FAQ has no passkey section, and the "co-developing passkey support...planned Q2 2025" language from their blog is the newest public statement found; no rpIdHash/parsing implementation is publicly visible. Treat Squads passkey internals as **UNVERIFIED/not yet public**. [Squads mainnet blog](https://squads.xyz/blog/squads-smart-account-program-live-on-mainnet), [Squads FAQ](https://docs.squads.so/main/additional-resources/faqs).

**Turnkey and Privy don't verify passkeys on-chain at all.** Both use the passkey purely as a *local authentication factor* gating access to a keypair/MPC-share held in a TEE/enclave (Turnkey: HSM/TEE; Privy: TEE + optional MPC), which then produces an ordinary **Ed25519** Solana signature server-side. The passkey P-256 signature never touches Solana consensus or the secp256r1 precompile — it authenticates a request to an off-chain signer. This is the dominant "custodial-ish embedded wallet" pattern and structurally different from Warden/LazorKit's fully on-chain root-of-trust. [Turnkey embedded wallets](https://www.turnkey.com/embedded-wallets), [Helius Solana Passkeys](https://www.helius.dev/blog/solana-passkeys), [Blueshift embedded-wallets course](https://learn.blueshift.gg/en/courses/embedded-wallets/passkeys-webauthn).

**Solana Mobile (Saga) does not use passkeys/secp256r1 at all** — its Seed Vault is a QSEE/TEE-backed Ed25519 seed custodian (Argon2id-derived unlock, 10-attempt wipe), a completely separate hardware-attestation model, not WebAuthn. [Offside Security "Saga of Saga" Part 2](https://blog.offside.io/p/saga-of-saga-part-2-digging-into-solana).

**Ecosystem-level passkey risk (Aug 2026, cross-platform, not Solana-specific but directly relevant)**: three disclosed 2026 attacks — SpecterOps (Windows cached YubiKey signature replay through Entra), Unit 42 (malware extracting Chrome's 32-byte Security Domain Secret to recover *all* synced Google Password Manager passkey private keys), and a Windows Hello session-hijack (Mollema) — show that **synced** passkeys are not uniformly phishing-*and*-malware resistant; a compromised endpoint session can, in some ecosystems, forge fresh WebAuthn assertions without a fresh biometric. Recommended mitigations: enforce UV, and treat "passkey store / recovery flow / browser memory" as credential-sensitive attack surface. [The Hacker News, Aug 2026](https://thehackernews.com/2026/08/new-passkey-attacks-can-recover-synced.html).

## What Warden should adopt / change

1. **Mandate UV, not just UP, and verify it against your own review claim** — confirm the on-chain `root_verify` path actually branches on the UV bit (0x04) and rejects UP-only assertions; LazorKit's UV-parsed-but-unenforced gap is a real-world instance of exactly this slip, worth a targeted test.
2. **Adopt LazorKit's "store rpIdHash once at registration, compare on every use" pattern** — it saves a `sol_sha256` per tx over recomputing from origin, and Warden's own spike notes (`rpIdHash = SHA-256 of full chrome-extension://<id> origin`) suggest the same precomputation is available; confirm Warden already does this rather than rehashing per-call.
3. **Stress-test the strict scanner against LazorKit's exact regression class**: a string value containing an unescaped `}`/`{`/`,` byte-sequence that could desync brace-depth tracking if any code path doesn't fully consume string bodies char-by-char. Port their test case (`{"tokenBinding":{"id":"x}y"},"challenge":"real"}`) into Warden's own fuzz/unit suite verbatim.
4. **Consider LazorKit's dual replay defense (monotonic counter + slot-freshness window) as a design cross-check** against Warden's "consumed nonce" — the counter approach is simpler to audit (no nonce-set storage/pruning) but strictly serializes signing (a dropped/out-of-order tx desyncs the odometer and requires a resync path); confirm Warden's consumed-nonce design has an analogous resync/expiry story and doesn't strand a user on a lost/replayed nonce.
5. **Explicitly do not trust the WebAuthn hardware signature counter** for clone detection (both LazorKit's comment and general WebAuthn guidance agree synced passkeys break it) — rely solely on the on-chain nonce/counter, which Warden already does.
6. **Reject cross-instruction offset references and CPI** the way LazorKit does (`0xFFFF`-only offsets, `stack_height > 1` reject) — cite as confirmation these are the two industry-standard hardening moves for this precompile pattern, not overkill.
7. **Given the Aug-2026 synced-passkey extraction attacks, document in Warden's threat model whether it will accept synced (iCloud/Google) passkeys as root at all**, or restrict v1 to device-bound/platform authenticators — this is a live, unresolved ecosystem risk, not a hypothetical.
