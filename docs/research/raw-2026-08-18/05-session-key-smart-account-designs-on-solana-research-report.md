# Session-Key & Smart-Account Designs on Solana — Research Report (2026-08-18)

## Findings

**Swig (Anagram)** — `github.com/anagrambuild/swig-wallet`, AGPL-3.0, program in `/program`, `/state`, `/instructions`. Role-based model: each wallet supports up to 65,000 roles, each pairing an *authority* (keypair, social login, session key) with a *permission* set ([blog.anagram.xyz](https://blog.anagram.xyz/introducing-swig-unlocking-the-future-of-smart-wallets-on-solana-and-ethereum/), [solanacompass.com](https://solanacompass.com/learn/breakpoint-25/swig-the-future-of-smart-wallets-on-solana)). The `Permission` enum (`state/src/action/mod.rs`) has ~27 variants: `SolLimit`/`SolRecurringLimit`, `TokenLimit`/`TokenRecurringLimit`, destination-scoped siblings (`SolDestinationLimit`, `TokenDestinationLimit`), CPI controls `Program` / `ProgramScope` / `ProgramAll` (unrestricted CPI) / `ProgramCurated` (allowlist-only), plus `StakeLimit`/`StakeRecurringLimit`/`StakeAll`, `SubAccountV2*`, `ManageAuthority`, `ReplaceAuthority`. Recurring-limit reset (`sol_recurring_limit.rs`) is **period-aligned, not last-use-anchored**: `last_reset = (current_slot / window) * window` — a deterministic floor to fixed slot buckets (e.g., every 100 slots), not a rolling window keyed off when the limit was last touched. Audited by Accretion (per repo README; report not publicly fetchable).

**Squads v4** — `github.com/Squads-Protocol/v4`. `SpendingLimit` account: `period` enum (`OneTime`/`Day`/`Week`/`Month`), `remaining_amount`, `last_reset`, `mint` (default pubkey = SOL), `destinations` allowlist (empty = unrestricted), independent `members` list that survives multisig membership changes. Use logic: `remaining_amount.checked_sub(amount)`; reset is **last-use-anchored rolling**: if `now - last_reset > period_seconds`, restore `remaining_amount` and advance `last_reset += periods_passed * period_seconds` (drifts from wall-clock day boundaries over idle periods, unlike Swig's epoch-floor). Time locks: configurable None/1h/1d/1w/custom, delay starts once a proposal reaches the "ready to execute" (Approved) threshold; `cancel_proposal` requires Voter permission and only applies to Approved or stale proposals ([docs.squads.so time-locks](https://docs.squads.so/main/navigating-your-squad/settings/time-locks), [docs.squads.so cancel-proposal](https://docs.squads.so/main/development/typescript/instructions/cancel-proposal)). Also ships Roles, sub-accounts, batch/ALT support, and a separate "Smart Account Program" line with session keys/passkeys/direct debits ([squads.xyz v4 announcement](https://squads.xyz/blog/v4-and-new-squads-app)).

**Squads audits** — Trail of Bits, Neodyme, OtterSec (all 2023), Certora formal verification (Oct 2023, repeated Dec 2023–Jan 2025), plus repeat Neodyme/OtterSec passes in 2024 ([docs.squads.so security-audits](https://docs.squads.so/main/security/security-audits/squads-protocol-v4), [Neodyme PDF](https://neodyme.io/reports/Squads-Multisig-v4.pdf), [OtterSec 2024 PDF](https://github.com/Squads-Protocol/v4/blob/main/audits/ottersec_squads_v4_audit_2024.pdf)). One concretely surfaced Neodyme item: **ND-SQD1-I2 "Reentrancy Voting Possible"** (Info, Resolved) — a user could re-enter the vote instruction from within a proposal's own CPI; recommended fixes were disallowing vote-instruction reentrancy or adding a transitory `Proposal::Executing` state (source: search snippet of the audit PDF via [Accretion's Solana tips](https://accretionxyz.substack.com/p/r0bres-100-daily-solana-tips) — UNVERIFIED against full PDF text, which failed to parse). Certora's conclusion was "no major security flaws" ([squads.xyz certora post](https://squads.xyz/blog/certora-formal-verification-squads-protocol-v4)) but the exact proved invariant list wasn't accessible as text. Squads runs a tiered bug bounty: theft $300k, fund-freezing $200k, replay $25k, unauthorized config change $10k ([squads.xyz v4-security-measures](https://squads.xyz/blog/v4-security-measures)).

**Fuse wallet** is a consumer wallet built directly on Squads Protocol: 2-of-3 multisig smart account, spending limits (token/amount/daily-weekly-monthly), key rotation, recovery keys, `fuseSOL` gas abstraction — i.e., proof Squads' primitives already power a shipped retail product ([fusewallet.com](https://fusewallet.com/blog/fuse-solana-s-first-smart-wallet)).

**MagicBlock/Gum session keys** — Gum (social protocol) shut down; MagicBlock now maintains the open-sourced Session Keys protocol (`dhruvja/session-keys`) as a *separate* program issuing ephemeral keypairs + session tokens, integrated into the Solana Unity SDK to avoid repeated wallet popups in games ([magicblock.xyz/blog/session-keys](https://www.magicblock.xyz/blog/session-keys), [docs.magicblock.gg](https://docs.magicblock.gg/pages/tools/session-keys/integrating-sessions-in-your-program), [blockchain.news](https://blockchain.news/postamp?id=solana-gum-protocol-shuts-down)). This is architecturally distinct from Warden/Swig/LazorKit: caps live in a delegate token program the dApp trusts, not in the funds-holding program itself.

**Lazor Kit** — `github.com/lazor-kit/program-v2`. Secp256r1/WebAuthn passkeys on-chain, non-custodial. Session keys are PDAs seeded `["session", wallet, session_key]` with absolute slot-based expiry (max 30 days) and up to **16 immutable rules per session**: SOL/token caps (lifetime, recurring-window, per-tx), per-mint restriction, program allow/blacklist for CPI targets. Notably includes explicit "vault-invariant defenses against `System::Assign`/`SetAuthority`/`Approve` escapes" and a `stack_height` check for CPI-reentrancy protection. Roles: Owner (full control) → Admin (session/authority lifecycle) → Spender (execute-only). Replay protection uses a monotonic `u32` counter per authority, working across multiple synced passkeys.

**Backpack** — largely a classical keypair wallet with an xNFT plugin runtime (apps execute *inside* the wallet UI); no delegated bounded-session-key or spending-limit smart-account layer found — not directly comparable to Warden's model ([learn.backpack.exchange](https://learn.backpack.exchange/wallet/solana)).

**Helius/Squads AA write-ups** frame Solana "account abstraction" as: smart wallets = executable program accounts (not simple keypairs); passkeys unlock a session that grants scoped access to an Ed25519 signing key; paymaster fee sponsorship ([helius.dev/blog/solana-smart-wallets](https://www.helius.dev/blog/solana-smart-wallets), [helius.dev/blog/solana-passkeys](https://www.helius.dev/blog/solana-passkeys), [squads.xyz account-abstraction-use-cases](https://squads.xyz/blog/account-abstraction-use-cases)) — this is exactly Warden's passkey-root → Ed25519-session-key pattern, independently converged on by the ecosystem.

## What Warden should adopt / change

1. **Anchor bucket resets to fixed epoch boundaries (Swig-style `floor(slot/window)*window`)**, not last-use-anchored rolling (Squads-style). Epoch-aligned buckets are predictable/auditable and closer to non-gameable than an anchor that drifts with `periods_passed * period` from whenever the key was last used.
2. **Add destination-scoped sub-limits** (Squads' `spending_limit.destinations`, Swig's `SolDestinationLimit`/`TokenDestinationLimit`) on top of Warden's account-wide day/30-day buckets — let a session key be capped *and* pinned to a specific counterparty (e.g., only its own dApp treasury).
3. **Close the CPI-escape class LazorKit explicitly defends against**: Warden's before/after conservation check on `execute` should explicitly detect/block `SetAuthority`/`Approve`/`System::Assign`-style calls that grant future drain rights without moving balance now — a naive balance-diff check misses this.
4. **Add a `stack_height`/CPI-reentrancy guard** on the `execute`/adapter-registry instruction (LazorKit's pattern), and consider Squads' fix for ND-SQD1-I2 — a transitory "Executing" state — for any Warden instruction that itself invokes CPI mid-approval-flow.
5. **Formalize timelock/cancel as an explicit state machine** (Squads: Approved → time-locked → Executable, cancelable anytime by any Voter while pending) rather than an implicit delay, and expose cancel as a first-class guardian/owner action.
6. **Invest in formal verification of the bucket/conservation invariants** (Certora-style) given Squads treats this as materially raising assurance beyond audits alone.
7. **Model planned guardians/recovery on Squads' member+spending-limit primitives** (validated in production via Fuse) rather than re-deriving from scratch.
8. Warden's choice to enforce caps **inside the funds-holding program itself** (vs. MagicBlock/Gum's separate session-token program) is a genuinely stronger trust boundary — worth stating as a validated design decision, not a gap.
