# Browser-Extension Wallet Security Engineering (MV3, 2024–2026) — Research Report

## Findings

**Keyring isolation / supply-chain hardening (MetaMask precedent)**
- MetaMask uses **LavaMoat**, a SES (Secure ECMAScript)-based hardening toolkit that runs at three points — dependency install, build, and runtime — to sandbox third-party npm code with capability-scoped Compartments, limiting what a compromised transitive dependency can reach (no ambient `fetch`, `XMLHttpRequest`, or filesystem unless explicitly granted). ([metamask.io](https://metamask.io/news/using-lavamoat-to-solve-software-supply-chain-security))
- **LavaDome** extends this to the DOM: sensitive UI (seed-phrase display, password fields) renders inside encapsulated ShadowDOM trees so that injected/compromised third-party JS in the same page cannot read or tamper with those elements. ([github.com/LavaMoat/LavaDome](https://github.com/LavaMoat/LavaDome))
- Reproducible builds remain an **unsolved gap even for MetaMask** — its build is not bit-for-bit deterministic across platforms, it lost Mozilla add-on fast-track status over this, and competitors (Rabby) are cited as ahead on verifiable-build posture. ([github.com/MetaMask/metamask-extension#3999](https://github.com/MetaMask/metamask-extension/issues/3999); [cryptoslate.com](https://cryptoslate.com/crypto-wallets/metamask-review/))

**MV3 service-worker lifetime / unlock state**
- MV3 kills persistent background pages; MetaMask's service worker goes idle after Chrome's ~30s inactivity window and previously could not be resurrected without a full extension reinstall in some states — they shipped a keep-alive/restart-logic patch extending liveness to 45 minutes for connected dApps and rebuilding phishing-blocklist state on wake. ([github.com/MetaMask/metamask-extension#16075](https://github.com/MetaMask/metamask-extension/pull/16075); [#14049](https://github.com/MetaMask/metamask-extension/issues/14049); [#16488](https://github.com/MetaMask/metamask-extension/pull/16488)). Implication: **unlocked-key material or session state cannot safely live in service-worker memory across restarts** — it must be re-derived from `chrome.storage.session` (in-memory, cleared on browser close) or require re-auth, and any auto-lock/idle-timeout logic must account for worker suspension, not just wall-clock idle (tracked as an open MetaMask bug: idle timer ignoring VM/worker sleep). ([github.com/MetaMask/metamask-extension#15503](https://github.com/MetaMask/metamask-extension/issues/15503))

**Provider injection hardening**
- Standard MV3 pattern: an **isolated-world content script** bridges via `postMessage`/`window.postMessage` to a **main-world injected script** that exposes `window.ethereum`/EIP-1193, with the background service worker as the trust boundary that validates message origin before touching keys. ([davidwalsh.name](https://davidwalsh.name/inject-global-mv3); example implementation: [dogeshit-wallet](https://github.com/dogeshitmeme/dogeshit-wallet))
- **EIP-6963** (Multi Injected Provider Discovery) replaces the single-global `window.ethereum` race condition with an event-based announce/request protocol (`eip6963:announceProvider`/`requestProvider`), reducing both provider-clobbering by malicious extensions and passive fingerprinting if wallets delay injection until requested. ([eips.ethereum.org/EIPS/eip-6963](https://eips.ethereum.org/EIPS/eip-6963); [metamask.io](https://metamask.io/news/how-to-implement-eip-6963-support-in-your-web3-dapp))

**Transaction-simulation / anti-drainer vendors**
- **Blowfish**: pre-signing scan API (EVM + Solana, 10+ chains) returning human-readable state-change previews, approval risk, and a suggested action; wallets are told to re-simulate every ~5s while the confirmation screen is open to avoid stale-simulation bypass, and it supports Gnosis Safe multisig threshold overrides. ([docs.blowfish.xyz](https://docs.blowfish.xyz/docs/wallet-integration-guide))
- **Blockaid**: two-stage simulation+validation before signature generation, plus proactive internet-wide dApp scanning (~15M sites/day, 500+ new malicious dApps/day) and a token-blocklist; integrated into Coinbase, MetaMask, Safe, World App. ([privy.io](https://privy.io/blog/transaction-scanning); [blockaid.io/platform](https://www.blockaid.io/platform))
- **Kerberus/Pocket Universe** (Kerberus acquired Pocket Universe Aug 21 2025): consumer-facing extension, intercepts the sign prompt, simulates, flags excessive-permission drainer patterns and counterfeit tokens; claims 99.9% detection across 1000+ EVM chains + Solana and offers up to $30k reimbursement coverage. ([kerberus.com](https://www.kerberus.com/articles/pocket_universe/); [theblock.co](https://www.theblock.co/post/367826/crypto-security-firm-kerberus-acquires-power-universe-anti-fraud-browser-extension-ethereum-solana-wallets))
- Caveat: Coinspect's case study documents concrete **simulation-bypass classes** (state dependent on block context, front-running-sensitive sims, multi-step approval chains) — simulation is a strong filter, not a guarantee. ([coinspect.com](https://www.coinspect.com/blog/transaction-simulation-challenges/))

**Address poisoning / clipboard hijack**
- Attackers zero-value-transfer from vanity look-alike addresses into a victim's tx history, betting on copy-from-history habits. MetaMask shipped 2026 look-alike detection comparing pasted addresses against history; Gem Wallet added a one-tap saved-contacts flow (Jul 2026) as a structural fix. Etherscan now hides zero-value transfers by default. ([kerberus learn](https://www.kerberus.com/learn/web3-security-tools/), [cryptodaily.co.uk](https://cryptodaily.co.uk/2026/08/crypto-address-poisoning-fake-histories))
- Microsoft (Jun 2026) documented a Windows **"Crypto Clipper"** worm — USB `.lnk` propagation, ~500ms clipboard polling, swaps copied addresses for attacker addresses from a 15,500-address bank, exfiltrates over Tor. This is OS-level, not extension-level, but wallets should **never trust an unconfirmed paste** — always render the full address plus a checksum/identicon at the confirm screen. ([microsoft.com/security/blog](https://www.microsoft.com/en-us/security/blog/2026/06/17/crypto-clipper-uses-tor-worm-like-propagation-for-persistence-control/))

**Major incidents — malicious update / takeover vectors (highest relevance to Warden)**
- **Trust Wallet, Dec 24 2025**: attacker used a **leaked Chrome Web Store publisher API key** to push malicious v2.68 directly, bypassing normal review/CI; it exfiltrated decrypted mnemonics via a legitimate PostHog SDK repurposed to beacon to a look-alike domain (`api.metrics-trustwallet[.]com`). $7–8.5M stolen, 2,520–2,596 wallets. Root enabler traced to **Shai-Hulud 2.0**, a self-propagating npm worm (Nov 24 2025, 800+ packages, 27,000+ malicious versions, ~400k secrets leaked from 30k GitHub repos) that harvested the CI/publishing credentials. ([thehackernews.com](https://thehackernews.com/2025/12/trust-wallet-chrome-extension-bug.html); [microsoft.com Shai-Hulud 2.0](https://www.microsoft.com/en-us/security/blog/2025/12/09/shai-hulud-2-0-guidance-for-detecting-investigating-and-defending-against-the-supply-chain-attack/); [securityweek.com](https://www.securityweek.com/shai-hulud-supply-chain-attack-led-to-8-5-million-trust-wallet-heist/))
- **QuickLens, Feb 2026**: legitimate extension sold on a broker marketplace (ExtensionHub) to a new owner who pushed a malicious v5.8 to ~7,000 users — stripped CSP/security headers via `declarativeNetRequestWithHostAccess`, delivered ClickFix malware that stole MetaMask/Phantom seed phrases. Google removed it and auto-disabled installs. ([thehackernews.com/2026/03](https://thehackernews.com/2026/03/chrome-extension-turns-malicious-after.html); [bleepingcomputer.com](https://www.bleepingcomputer.com/news/security/quicklens-chrome-extension-steals-crypto-shows-clickfix-attack/))
- **Fake imToken clone, Feb 2026**: malicious extension ("lmΤoken Chromophore," homoglyph name) posed as a color tool, used fake reviews/branding; imToken has **no real extension**, only mobile — any extension claiming the brand is fraudulent by definition. ([cyberpress.org](https://cyberpress.org/fake-imtoken-extension-steals/))
- **"Safery" fake Ethereum wallet, Nov 2025**: backdoor exfiltrates seed phrases by encoding them into Sui addresses and broadcasting microtransactions to a threat-actor Sui wallet — novel covert-channel exfiltration that evades network-based DLP. ([thehackernews.com](https://thehackernews.com/2025/11/fake-chrome-extension-safery-steals.html))
- Aggregate: Chainalysis figures cited put personal-wallet-compromise losses at **$713M in 2025** (~20% of $3.4B total crypto theft). ([cryptoslate.com aggregate cited in search](https://cryptoslate.com/how-browser-extensions-expose-your-crypto-to-a-fatal-design-flaw-that-the-industry-ignored-bleeding-713m-in-2025/) — UNVERIFIED, WebFetch 403'd, figure only from search snippet, not primary-source-confirmed).

**WebAuthn PRF in extensions**
- Chrome/Chromium-based browsers support the WebAuthn PRF extension; as of the request date Chrome has PRF-on-create support (search snippet cites "Chrome 147" — **UNVERIFIED**, plausible given cadence but not confirmed against a primary changelog), Windows Hello on Win11 25H2 returns PRF via `WEBAUTHN_API_VERSION_8`, and platform authenticator support (iCloud Keychain, Android) is broadly solid by 2026. Relevant to Warden only if it ever wants a PRF-derived symmetric key wrapping local session-key material — the **on-chain P-256 root stays the security boundary**, PRF would only harden local storage. ([corbado.com](https://www.corbado.com/blog/passkeys-prf-webauthn); [issues.chromium.org/40140659](https://issues.chromium.org/issues/40140659))

**Chrome Web Store governance**
- CWS mandates 2-Step Verification for publishing accounts (in force since 2021, still enforced 2026) and announced further Developer Program Policy tightening effective Aug 1 2026 — yet **the Trust Wallet incident happened entirely within these rules** via a leaked API key, proving 2FA-on-login is insufficient without separate scoped, rotatable, short-lived **publishing/release credentials** isolated from developer laptops and CI secret stores. ([developer.chrome.com/blog/cws-policy-updates-2026](https://developer.chrome.com/blog/cws-policy-updates-2026))

**Backpack (xNFT model)** — sandboxes third-party dApp code as installed "xNFTs" running inside wallet-controlled iframes/sandboxes with per-app explicit permissions rather than per-website `window.ethereum` connect, which structurally denies phishing sites the ability to mimic in-wallet UI. Interesting model but adds significant surface (an app runtime inside the wallet) — not obviously right for Warden's leaner PDA/session-key model. ([alchemy.com/overviews/xnft](https://www.alchemy.com/overviews/xnft))

## What Warden should adopt / change

1. **Split publishing credentials from dev/CI secrets, now.** The single highest-value 2026 lesson is Trust Wallet: a leaked CWS API key (sourced from an npm-worm-compromised CI) let an attacker ship a signed malicious update with zero code review. Warden should keep the CWS publisher token in a separate, short-lived, manually-gated release process (a dedicated release machine or a human-in-the-loop OAuth flow), never in general CI env vars reachable by `npm install` of arbitrary deps.
2. **Adopt SES/LavaMoat-style dependency hardening** for the extension bundle — Warden already has a security-first two-model build loop (Claude + Codex review); add a runtime capability-attenuation layer so a compromised transitive npm dep (the Shai-Hulud vector) cannot reach `fetch`/network/storage. Given Warden is new and can architect this from day one at lower cost than MetaMask's retrofit.
3. **Treat the service worker as untrusted-for-secrets.** Never hold decrypted session-key material in worker global scope across idle cycles; re-derive/re-fetch from `chrome.storage.session` on wake, and make the auto-lock timer clock-based against wall time, not worker-liveness (MetaMask's own open bug on this).
4. **Isolated-world/main-world provider bridge + EIP-6963**, not legacy singleton `window.ethereum` — reduces provider-clobbering/fingerprinting and is now the ecosystem standard; validate all cross-world postMessage origins in the isolated-world script before forwarding to the background.
5. **Integrate a transaction-simulation vendor (Blowfish or Blockaid) as a second opinion layered on top of Warden's own before/after conservation checks and adapter registry** — Warden's on-chain execute/adapter model already does deterministic conservation-check simulation server-side/on-chain, which is stronger than off-chain heuristic simulation, but a Blockaid/Blowfish dApp-reputation + token-blocklist feed adds pre-connect and pre-sign phishing-site coverage that Warden's architecture doesn't otherwise cover (malicious dApp UI itself, not just the tx payload).
6. **Address-poisoning UX**: since Warden already renders txs through the adapter/execute path, add a look-alike-address warning comparing paste targets against Warden's own recent-recipient history, and default to named/saved contacts for repeat sends, mirroring MetaMask 2026 and Gem Wallet.
7. **Publish (or plan) reproducible builds early** — this is a differentiator no major EVM wallet has solved cleanly; being open-source + build-reproducible from v1 is cheap now and expensive to retrofit later (MetaMask's Firefox fast-track loss is the cautionary tale).
8. **Do not build an xNFT-style in-wallet app runtime** — Backpack's model adds meaningful attack surface for marginal phishing-resistance gain that Warden's adapter-registry + EIP-6963-style provider bridge should already achieve at the transaction layer.
9. **CSP**: MV3's default extension-page CSP already forbids remote script/eval; audit that no wallet-controlled page falls back to `'wasm-unsafe-eval'` or remote-hosted script (the QuickLens incident depended on stripping headers via elevated `declarativeNetRequest` permission — Warden should avoid ever requesting broad `webRequest`/`declarativeNetRequestWithHostAccess` host permissions the popup/background doesn't strictly need).
