# Warden Wallet — Prior Art Deep Dive: Squads v4/v5, Swig, LazorKit

*Sources cloned/read directly: [Squads-Protocol/v4](https://github.com/Squads-Protocol/v4) (multisig-first, threshold≥1), [Squads-Protocol/smart-account-program](https://github.com/Squads-Protocol/smart-account-program) (v5 — underlying protocol for Fuse; "Squads Fuse" itself has no separate public repo — see Open Questions), [anagrambuild/swig-wallet](https://github.com/anagrambuild/swig-wallet), [lazor-kit/lazor-kit](https://github.com/lazor-kit/lazor-kit) + submodule [lazor-kit/program-v2](https://github.com/lazor-kit/program-v2). All four PDFs in-repo were extracted with `pdftotext` and read directly.

## Findings

**Squads v4** — Anchor-based, RBAC via `Multisig`/`Permission` bitflags; `SpendingLimit` account (`state/spending_limit.rs`) has `amount`/`remaining_amount`/`period` (OneTime/Day/Week/Month) **plus a `destinations: Vec<Pubkey>` allow-list** — Warden has no analog to per-session destination restriction today. `vault_transaction_execute.rs` gates execution on `member_has_permission(Execute)` + `Proposal::Approved` + `time_lock` elapsed, all via Anchor account constraints — clean but fully Anchor-idiomatic (no zero-copy/Pinocchio).
- **TOB-SQUADS-7 (High, Trail of Bits)**: `multisig_create.rs`'s PDA seed `create_key` is an unauthenticated `AccountInfo`, not a `Signer`. An attacker can front-run the creation tx, submit their own `members`/`threshold` for the same seed, and later drain vaults once the victim starts using the "already created" multisig. Fixed by requiring `create_key` to sign. (squads-v4/audits/trail_of_bits_squads_v4_security_audit.pdf, finding TOB-SQUADS-7)
- Squads' test suite (`tests/suites/`) is 100% TypeScript/mocha against a real `solana-test-validator` via `anchor test` — **no LiteSVM/bankrun, no Rust unit tests, no fuzzing** found anywhere in the repo (`package.json`: `"test": "anchor test -- --features=testing"`).
- v5 (`smart-account-program`) adds `transaction_execute_sync`/`settings_transaction_sync` — a fast single-round path that skips the propose→approve→execute lifecycle, closer to what a session-key "just execute" flow needs.

**Swig** (`anagrambuild/swig-wallet`, Pinocchio, zero-copy) — RBAC via `Position`+`Action` byte-packed records (`state/src/role.rs`, `action/mod.rs`); 26-variant `Permission` enum spans `SolLimit`/`SolRecurringLimit`/`SolDestinationLimit`(!)/`TokenLimit`/`TokenRecurringLimit`/`ProgramScope`/`ProgramCurated`/`SubAccountV2*`. `secp256r1.rs` (`state/src/authority/secp256r1.rs`) verifies WebAuthn via the same precompile-introspection pattern Warden uses, with `MAX_SIGNATURE_AGE_IN_SLOTS = 60`.
- **Accretion audit (2025-accretion-anagram-swig-audit-A25ANA2.pdf)**: 4 Critical, 3 High. Most instructive — **ACC-C1**: `sign_v1` validated *end-state field values* (balance, mint, owner-of-token-account-*field*) after CPI but never re-checked the **token account's actual program owner**. Attack: transfer-out → close account → reopen under an attacker program that fakes the same byte layout → passes all field checks → full drain with a 1-lamport-permission role. **ACC-C2**: no restriction on *which instructions* a limited role could submit at all — only end-state was checked, so any role could touch any account as long as it "looked" unchanged. **ACC-C3/C4**: `sub_account_sign_v1`/`withdraw_from_sub_account_v1` didn't validate the target account's parent-Swig ownership or discriminator.

**LazorKit** (`program-v2`, Pinocchio) — near-identical secp256r1/WebAuthn design to Warden's: raw `clientDataJSON` embedded in the auth payload (not reconstructed server-side), Instructions-sysvar introspection requiring `current_index - 1` to be the precompile, `sysvar_ix_index`-driven account lookup, strict offset/instruction-index checks (`auth/secp256r1/introspection.rs` rejects anything but `0xFFFF` cross-instruction indices), and `rpIdHash` precomputed once at authority creation and stored on-chain (fixed 145-byte authority: `header(48)+cred_hash(32)+pubkey(33)+rpIdHash(32)`) to save a `sol_sha256` syscall per execute. Uses a **u32 counter odometer** (`submitted_counter == on_chain_counter+1`) rather than Warden's consumed-nonce set. `Secp256r1Authenticator` explicitly rejects CPI callers via `get_stack_height() > 1`.
- Session/action model (`state/action.rs`, `processor/execute_actions.rs`) is a flat 11-byte-header action buffer appended after an 80-byte `SessionAccount`; 8 action types incl. `SolMaxPerTx` and `ProgramWhitelist`/`ProgramBlacklist`. The module doc literally says: **"Security model (learned from Swig wallet): balance increases ignored, only outflows count; state mutations only after all checks pass"** — i.e. LazorKit engineers read Swig's audit and hardened against exactly ACC-C1's class of bug: `TokenAuthoritySnapshot` freezes owner/delegate/close_authority pre-CPI and re-verifies them post-CPI (`verify_token_authorities_unchanged`), and `SolMaxPerTx` uses **gross** outflow (not net) specifically to block round-trip-CPI laundering of a per-tx cap.
- **Accretion program-v1 audit (2026-accretion-solana-foundation-lazorkit-audit-A26SFR1.pdf)**: 2 Critical, 2 High. **ACC-C1**: signed payload bound accounts by *index*, not pubkey — accounts could be reordered post-signature to redirect a transfer. **ACC-C2**: `RemoveAuthority`'s owner-role branch (`role==0`) skipped the "target belongs to this wallet" check entirely, enabling cross-wallet authority deletion. **ACC-H1**: `target_auth_pda`/`refund_dest` omitted from the signed payload → signature replay with substituted accounts → rent theft.
- Test/audit process is unusually mature: `docs/audit/DELTA_BRIEF.md` + `upstream-parity.txt` document per-file whether new code is byte-identical to an already-audited sibling repo (`lazorkit-protocol`), scoping re-audits to only the true delta. Dev-deps: `litesvm = "0.6"`, `p256 = "0.13"` (real ECDSA sigs generated in-process, no test-validator).

## What Warden should adopt / change

1. **Audit `create_account.rs`'s `owner_seed` for the TOB-SQUADS-7 pattern now.** Warden's `owner_seed: [u8; 32]` is a plain `CreateAccountArgs` field, not a signer — only `payer` is a `Signer`. If a pending `create_account` tx is visible pre-confirmation, an attacker could resubmit the same `owner_seed` with a different `root`/`policy` and win the PDA race. Squads' fix (require the seed-owning key to sign) is the template. Verify or add a negative test.
2. **Add an explicit `account.owner` (program-owner) check after CPI-execute**, not just field/balance diffing — this is exactly ACC-C1. Confirm Warden's execute/conservation-check path re-validates program ownership of every touched account post-CPI, not only lamports/token amounts.
3. **Snapshot+re-verify token-account owner/delegate/close_authority (not just balance)** around CPI, per LazorKit's `TokenAuthoritySnapshot` — closes the SetAuthority/Approve escape class the Swig audit found.
4. **Bind full account pubkeys — not indices — into every signed transcript** (root_verify and session-key signed message alike). Confirm `root_verify/transcript.rs` commits to actual pubkeys of every account the tx touches; index-only binding is LazorKit's ACC-C1.
5. **Use gross outflow for per-tx caps, net diff only for lifetime/day/30-day caps** — Warden's `MintCap{per_tx, per_day, per_30d}` should double-check `per_tx` is enforced on gross, not net, outflow to block round-trip CPI laundering.
6. **On any owner/admin short-circuit branch, still validate the target belongs to the same top-level account before skipping other checks** — LazorKit ACC-C2. Apply this to Warden's future guardian/recovery instructions.
7. **Treat an expired session's caps as fully exhausted, never as absent** — adopt LazorKit's explicit "expired action = 0 remaining" policy for `max_session_life_secs` boundary handling.
8. **Add a destination-address allow-list to session keys**, parallel to `ProgramWhitelist`/adapter registry — Squads v4's `SpendingLimit.destinations` is a distinct, complementary control axis Warden's cap model lacks.
9. **Adopt LazorKit's delta-brief/upstream-parity documentation practice** ahead of Warden's own audit — cheap now, saves real audit-hours later.
10. **Keep the LiteSVM+p256 in-process ECDSA harness (already in Warden's dev-deps)** but expand coverage to explicitly encode each CVE class above as a named negative test (account-reorder, cross-wallet-target, owner-bypass-after-CPI, expired-cap-spend) — Swig/LazorKit's test files are organized exactly this way (`cpi_program_permission_v2_test.rs`, `replace_authority_test.rs`, etc.).

## Open questions
- Is "Squads Fuse" itself open source, or only the underlying `smart-account-program` (v5) it's built on? No separate public Fuse repo was found — treat as UNVERIFIED/likely closed.
- Does Warden's `execute` path already satisfy items 2–3 above? Not confirmed — only `create_account.rs`/`session.rs` were read in this pass; `instructions/transfer.rs` and the adapter-registry conservation-check code were not.
- Certora's formal-verification report (Squads v4 and v5) was not read in this pass — likely contains invariant-writing lessons applicable to a future Warden formal-verification effort.

## Confidence
High for all source-quoted/audit-cited claims (file paths, PDF findings, line-level code). Medium for the Warden-specific `owner_seed` front-running observation — flagged from pattern-matching against TOB-SQUADS-7, not from a full read of Warden's create_account tests/handler.
