# Solana Wallet Standard / wallet-adapter / MWA vs. Smart-Account Wallets (2026)

## Findings

**1. The Wallet Standard's SIWS/signMessage verification path is hardcoded to Ed25519 — it structurally cannot verify a PDA/passkey account.** The reference `verifySignIn`/`verifyMessageSignature` utilities call `ed25519.verify(signature, signedMessage, publicKey)` directly, and `SolanaSignInOutput.signatureType` is typed as the single literal `'ed25519'` with a doc comment "If not provided, the signature must be Ed25519" ([signIn.ts](https://github.com/anza-xyz/wallet-standard/blob/master/packages/core/features/src/signIn.ts), [signMessage.ts](https://github.com/anza-xyz/wallet-standard/blob/master/packages/core/util/src/signMessage.ts), [signIn.ts (verify)](https://github.com/anza-xyz/wallet-standard/blob/master/packages/core/util/src/signIn.ts)). There is no branch for a program-verified/off-curve address. This is the Solana ecosystem's closest analogue to "no ERC-1271" — and unlike Ethereum, **no SIMD or accepted standard fills the gap**; a `gh` code search across GitHub for `isValidSignature`/`verify_offchain_signature`/`smart_wallet_signature` patterns on Solana returned nothing resembling a standardized smart-account signature-verification interface (search performed 2026-08-18).

**2. Mobile Wallet Adapter (MWA) has the same gap.** The spec's `authorize` response returns one `address`/`display_address` per account and assumes Ed25519 throughout; `sign_messages` and `sign_and_send_transactions` contain no smart-contract-wallet or non-Ed25519 provisions ([MWA spec](https://solana-mobile.github.io/mobile-wallet-adapter/spec/spec.html)). MWA is bridged into Wallet Standard via `@solana-mobile/wallet-standard-mobile` (598k weekly npm downloads as of 2026-08-18), inheriting the same limitation.

**3. secp256r1/passkey signature verification exists on-chain but is precompile-only, not wallet-tooling-aware.** SIMD-0075 (supersedes SIMD-0048) added the `Secp256r1SigVerify1111111111111111111111111` precompile specifically to enable passkey-based "account abstraction" ([SIMD-0075](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0075-precompile-for-secp256r1-sigverify.md)); SIMD-0565 adds BPF syscalls for the same curve, and SIMD-0152 covers the precompile design generally. None of these touch the wallet-adapter/Wallet-Standard/MWA client layer — Warden's own on-chain verification (secp256r1 precompile + Instructions-sysvar introspection) is the correct primitive, but the client-side "prove this to a dApp" problem is unsolved industry-wide.

**4. `PublicKey.isOnCurve()` is a widespread, silent rejection vector.** GitHub code search across the ecosystem shows `isOnCurve()` used as a wallet-address validity gate in Ledger Live, enKrypt, Bento, Koii, and as an SPL-token ownership gate throwing `TokenOwnerOffCurveError` unless `allowOwnerOffCurve: true` is passed explicitly (`okx/js-wallet-sdk`, `openbook-dex/openbook-v2`). A PDA is off-curve by construction, so any integration using the naive check breaks on a Warden address.

**5. Squads/Fuse do not use browser-extension + Wallet Standard for most dApp connectivity — they use an opt-in iframe adapter requiring dApp cooperation.** `@sqds/iframe-adapter` requires the target dApp to install the npm package, set a `Content-Security-Policy: frame-ancestors https://iframe-preview.squads.so` header, and get manually onboarded ("send us a message on Telegram or Discord for final testing") ([iframe-adapter README](https://github.com/Squads-Protocol/iframe-adapter)). This is an allowlist model, not a universal connect — it only works for dApps Squads has explicitly integrated. **Fuse** (Squads' consumer app, "powered by the same smart accounts that secure billions... on Solana," [fusewallet.com](https://fusewallet.com)) is architecturally a fintech app with curated DeFi/Jupiter integrations, not a general-purpose extension competing on universal dApp compatibility. **Swig** ([anagrambuild/swig-wallet](https://github.com/anagrambuild/swig-wallet), AGPL-3.0, audited by Accretion) is a program/protocol-level smart-account framework with no browser-extension frontend in its repo — it is infrastructure other wallets build on, not a connect strategy to compare directly.

**6. Warden's own Phase-0 spike inventory (2026-08-18) is the most concrete, primary data on real-world breakage** ([DECISION.md](https://github.com/Dr-Inker/warden-wallet/blob/main/docs/spikes/DECISION.md), [inventory.md](https://github.com/Dr-Inker/warden-wallet/blob/main/spikes/04-compat/inventory.md)): of 20 top Solana dApps inspected via source/IDL/production-bundle grep, **9 OK** (Jupiter, Raydium, Orca, Meteora, Kamino, Marinade, Drift core, Phoenix, marginfi — plain sign-and-send, wallet as fee payer only), **6 root-only** (Tensor, Sanctum, Parcl, Helium, Realms voting, Squads — clean signer shape but need manual `(program_id, discriminator)` adapter-registry entries, not architecturally broken), **1 unsupported firm** (Pump.fun — Privy-based SIWS login gate), plus caveated unsupported subflows: Realms Hub's separate SIWS profile layer, and Drift's opt-in "Swift" signed-order feature. 4 dApps (Jito, Solend/Save, Magic Eden, Photon) are provisional — evidence-blocked, not confirmed either way. Ephemeral `partialSign`'d dApp-generated keypairs (fresh mint/NFT accounts) are correctly *not* counted as co-signer breakage since they're independent of the wallet's own signature.

**7. Durable nonces + multisig co-signing:** no evidence of durable-nonce usage was found in any of the 20 inspected dApps (`inventory.md` col "Durable nonces?" — all "No — not found"), and Squads v4's own multisig approval flow is N *separate single-signer* transactions (`proposalApprove`, `vaultTransactionExecute` each have exactly one `isSigner:true` account, `member`), not one transaction with N partial signatures — so the classically-cited "durable nonce + multisig partial-sign" incompatibility class did not materialize as a live blocker in this sample; it remains a theoretical risk for any dApp that *does* build a nonce-advance + partial-sign flow, since a bounded session key cannot co-sign as the smart-account owner would.

## What Warden should adopt / change

- **Do not build a Squads-style iframe/allowlist connector as the primary strategy.** Warden's browser-extension + Wallet-Standard `execute`-wrapper approach (transparent to unmodified dApps) is structurally superior to Squads' opt-in iframe model for reach — keep it as the default path.
- **Treat SIWS/`signMessage` as an explicitly unsupported feature in v1, and say so in the UI** rather than silently failing `verifySignIn`. The blast radius per Warden's own inventory is narrow (1 firm dApp + 2 subflows of 20), not a top-20-wide blocker.
- **Prioritize the adapter-registry backlog by the `root-only` list** (Tensor, Sanctum, Parcl, Helium, Realms voting, Squads) — these are cheap wins, not compatibility fights.
- **Guard against `isOnCurve()` rejections proactively**: publish a short compatibility note / detect-and-warn UX for dApps/SDKs calling `allowOwnerOffCurve`-gated SPL helpers, since this is a silent throw, not a graceful degrade.
- **Re-derive every adapter discriminator from IDLs programmatically in Phase 2**, per Warden's own spike finding that only 2 of 15 seeded discriminators are ground truth (Meteora `swap`, Pump.fun `buy`); Jupiter v6 `route` — the one the swap path depends on — is unverified.
- **Watch for an emerging client-side smart-account signature standard** (there is none yet); if Wallet Standard ever adds a non-Ed25519 `signatureType`, Warden should be first to implement it rather than build a bespoke SIWS bypass.

## Open questions

- Does any dApp actually build a durable-nonce + multisig partial-sign transaction in production? Not found in this 20-dApp sample; UNVERIFIED beyond it.
- Whether Jito, Solend/Save, Magic Eden, Photon's connect flows fire `signMessage` post-wallet-selection is unresolved (Playwright-blocked/indirect evidence only) — needs a real extension-connected recheck.
- No public roadmap item at Solana Foundation or Anza for a Wallet-Standard non-Ed25519 `signatureType` was found; absence-of-evidence, not confirmed non-existence.
