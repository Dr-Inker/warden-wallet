# Warden Wallet vs. Real-World Solana Drain Techniques (2024–2026)

## Critical context: what Warden actually ships today (read from source, 2026-08-18)

Per the repo's own README and instruction set (`programs/warden/src/instructions/`: `create_account`, `freeze`/`unfreeze`, `grant_session`/`revoke_session`, `rotate_nonce`, `transfer` — nothing else), **only Phase 1A is merged**: passkey root verification, session per-tx/lifetime caps, and account-wide day/30-day buckets (`buckets.rs`). The `execute` instruction, adapter registry, staged transactions, and Jupiter `swap` are all **Phase 1B — plan committed today, not built** (README phase table; plan doc `docs/superpowers/plans/2026-08-18-warden-phase1b-execute-swap.md`). Guardians, recovery, and the **timelock queue are Phase 1C — not started**. Today, an over-threshold root transfer simply fails closed (`CapExceeded`) rather than being queued/cancellable (`transfer.rs:230-234` comment: "route is Phase 1B's timelocked `queue`"). Account creation is currently unauthenticated (squat risk until Phase 1B's proof-of-possession). This matters: **Warden today cannot connect to any dApp at all** — no CPI-issuing instruction exists — so most of the threats below are currently moot by absence of attack surface, not by design defense, and will only become live once Phase 1B ships.

## Findings by technique

- **Drainer kits (multi-chain, hardcoded drain address, "auto-drain delay" for stealth)** — real, active source confirms this pattern generically ([Monyancha/bonk-dragon config.js](https://github.com/Monyancha/bonk-dragon/blob/main/config/drainer.js)); Solana is one of many chains in these kits' address maps. **Today: N/A (no dApp connect exists). Post-1B: bounded** by session caps/buckets even if a malicious adapter slips a drain instruction through; **stopped** if the adapter registry categorically refuses unrecognized instruction shapes.
- **SetAuthority/delegate ("Account Authority Transfer")** — the single most Solana-specific and damaging pattern: reassigning an account's owner field permanently, distinct from EVM approval drains and irreversible even with the correct key ([research compiled from SlowMist-sourced incident data, digitaldrreamer/haveibeendrained](https://github.com/digitaldrreamer/haveibeendrained), citing a ~$3M Dec 2025/Jan 2026 case; corroborated pattern in [oh-ashen-one/solshield SOL3127](https://github.com/oh-ashen-one/solshield/blob/main/packages/cli/src/patterns/solana-batched-patterns-70.ts) and the 2022 Solana NFT phishing case in [SlowMist's handbook](https://github.com/slowmist/Blockchain-dark-forest-selfguard-handbook), line ~561). **Would stop it**, structurally: funds sit in a program-owned PDA reachable only through Warden's whitelisted instructions — no raw `SetAuthority`/`Approve` on the PDA's accounts is possible *unless/until* the Phase-1B adapter registry allowlists it. This is the load-bearing decision Warden must get right.
- **Address poisoning (dust transfers polluting tx history)** — a social/UI attack on the human, not the chain; caps/conservation **don't help** at all. Needs UI mitigation.
- **Fake airdrops / malicious metadata** — TxShield's risk scorer flags `MUTABLE_METADATA` and unrenounced authorities as real signals ([TxShield/TxShield sol-simulation-riskUtils.js](https://github.com/TxShield/TxShield/blob/main/server/services/solana/simulationSol/sol-simulation-riskUtils.js)). Viewing a token doesn't drain anything — the danger is the "claim" link's follow-through into an AAT/approve signature, so this reduces to the SetAuthority case above.
- **Priority-fee/instruction stuffing** — real, documented: the "Crypto Copilot" Chrome extension silently inserted extra `SystemProgram.transfer` instructions into legitimate Raydium swaps, skimming 0.05% per trade; "STMT" (single-tx multi-transfer) phishing drained 4+ token types per signature, with one address (`Gck5…1VX4`) logging 1,639 such txs (per the digitaldrreamer compilation). **Best match to Warden's design**: the `execute` before/after conservation check is *exactly* the countermeasure — but only if it checks every mint touched by the CPI, not just the "primary" swap asset, or a side-skim slips past a narrowly-scoped conservation check.
- **Jupiter/limit-order abuse** — I could not reach a primary Jupiter security source this session (search budget exhausted, `developers.jup.ag/docs/security` 404'd). **UNVERIFIED reasoning only**: the plausible risk is a fake frontend routing through a look-alike program ID, or a limit-order program that custodies funds without on-chain min-out enforcement. Warden's adapter registry pinning the real Jupiter program ID as an immutable constant would close the impersonation vector; **not addressed by caps alone**.
- **Seed-phrase malware / clipboard hijackers** — Warden's no-seed-phrase-by-default root **eliminates seed-phrase theft as a root-compromise vector** (matches SlowMist's general clipper/malware findings, handbook line ~882-896). Clipboard hijacking that swaps the *destination address at signing time* is a UI-truth problem the passkey design does not solve — only bounds the blast radius to the session cap.
- **Compromised dApp front-ends / supply chain** — the `@solana/web3.js` npm compromise is a confirmed, primary-sourced incident: [GHSA-jcxm-7wvp-g6p5 / CVE-2024-54134](https://github.com/solana-labs/solana-web3.js/security/advisories/GHSA-jcxm-7wvp-g6p5), Dec 3 2024, malicious versions 1.95.6/1.95.7 live ~5 hours, exfiltrating private keys. **Warden's own model is well-matched** for a compromised *counterparty* dApp (registry + conservation don't trust the dApp's displayed intent) but does **nothing** for a compromise of Warden's own extension/`packages/core` supply chain — `SECURITY.md` doesn't yet mention lockfile/provenance hardening.
- **Telegram bot wallets** — architecturally orthogonal (custodial hot wallets, not self-custody extensions); the DEXX Nov 2024 breach (~$30M/8,612 wallets, per the compiled research) is exactly the class of loss Warden's on-chain caps are designed to bound *if* the keys had been session keys under caps rather than a custodian's plaintext store.

## What Warden should adopt / change

1. **Hard deny-list, not just an allowlist**: the adapter registry should categorically refuse `SetAuthority`, `Approve`, `CloseAccount`, and Token-2022 permanent-delegate/transfer-hook extensions for any (program, discriminator) — no adapter mapping should ever be able to authorize these, given they're the #1 real-world Solana drain vector.
2. **Multi-mint conservation, not primary-asset conservation** — snapshot *every* balance touched by an `execute` CPI, not just the swap's named in/out mint, to catch Crypto-Copilot-style side skims.
3. **Pin partner program IDs as immutable on-chain constants** (Jupiter et al.) in the adapter registry — never trust a dApp-supplied route/program.
4. **Ship proof-of-possession account creation before any public exposure** — the squat window is real today.
5. **Don't ship UI copy implying "large transfers are timelocked" until Phase 1C's queue actually exists** — today over-cap root transfers fail closed, they aren't cancellable.
6. **Default session caps low**, since every technique above (AAT, STMT, approval drains) tries to maximize value extracted from one signature.
7. **UI-level address-poisoning defense**: never autofill a destination from raw tx history; distinguish saved contacts visually.
8. **Harden Warden's own supply chain** (lockfile pinning, CI provenance) — the largest real loss event in this research was a *library* compromise, not a protocol flaw.
