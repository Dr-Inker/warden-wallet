# Solana Runtime Facts for Smart-Account Wallets — 2026 Update

## Findings

**Transaction size/format — still 1,232 B on mainnet; v1 not live.** SIMD-0296 ("Larger Transaction Size," status **Review**) proposes raising the limit to 4,096 B, gated on the new `v1` message format defined by SIMD-0385 ("Transaction V1 Format," status **Review**, created 2025-10-24). Neither carries a feature key yet ("fill in ... once accepted"), so **1,232 B remains the hard limit today**. SIMD-0385's `v1` format drops ALTs entirely (addresses must be listed in full) and caps `num_accounts ≤ 64`, `num_instructions ≤ 64`, `signatures ≤ 12`, `accounts/instruction ≤ 255`, and moves compute-budget config into a `TransactionConfigMask` header field instead of `ComputeBudgetProgram` instructions. [SIMD-0296](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0296-larger-transactions.md) · [SIMD-0385](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0385-transaction-v1.md)

**CPI depth is still 4 — SIMD-0268 is Accepted but NOT activated on mainnet.** Agave's `program-runtime/src/execution_budget.rs` (master) hardcodes `MAX_INSTRUCTION_STACK_DEPTH: usize = 5` (depth starts at 1 for the top-level tx instruction ⇒ 4 nested CPI levels) and `MAX_INSTRUCTION_STACK_DEPTH_SIMD_0268: usize = 9` (8 nested) behind a `simd_0268_active` bool. I queried mainnet-beta RPC directly for the feature pubkey `6TkHkRmP7JZy1fdM6fg5uXn76wChQBWGokHBJzrLB3mj` (`getAccountInfo`, slot 440,130,853, 2026-08-18) → **`value: null`** — the feature account doesn't exist, i.e. it hasn't even been queued for activation despite SIMD status "Accepted." **Do not build any Phase-1B/1C logic assuming depth-8 CPI.** [source](https://raw.githubusercontent.com/anza-xyz/agave/master/program-runtime/src/execution_budget.rs) · [SIMD-0268](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0268-raise-cpi-nesting-limit.md)

**CPI account-info limit 64→255 IS already live.** SIMD-0339's feature (`H6iVbVaDZgDphcPbcZwc5LoznMPWQfnJ1AM7L1xzqvt5`) returned a populated, Feature-program-owned account (activation slot ≈402,996,096, well before current slot) — confirmed active via RPC. CPI calls can now pass up to 255 `AccountInfo`s and are metered for serialized account-infos/metas, useful if Warden's `execute` adapter ever needs to pass through large Jupiter-style account sets. [SIMD-0339](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0339-increase-cpi-account-info-limit.md)

**Account-lock limit is 128, not 64.** `solana-sdk` `transaction/src/sanitized.rs` hardcodes `pub const MAX_TX_ACCOUNT_LOCKS: usize = 128;` ("chosen ... for the Neon EVM implementation"), unconditional in current code — the old `increase_tx_account_lock_limit` feature-gate (Agave PR #27241, "increase tx account lock limit to 128") is long-fused-in. **Solana's own docs page still says this feature is "currently inactive," which is stale** — treat solana.com docs as secondary and prefer source. [raw source](https://raw.githubusercontent.com/anza-xyz/solana-sdk/master/transaction/src/sanitized.rs)

**Block CU limit is 60M today, 100M path staged; per-account limit is 40% dynamic.** `cost-model/src/block_cost_limits.rs` on master: `MAX_BLOCK_UNITS = MAX_BLOCK_UNITS_SIMD_0256 = 60_000_000`, `MAX_WRITABLE_ACCOUNT_UNITS = 24_000_000` (= 40% of 60M, matching SIMD-0306's "20M/40%-of-block" writable-account cap rather than the old static 12M). SIMD-0286 (100M) exists as a defined constant (`simd_0286_block_limit()`) but isn't the active default. [source](https://raw.githubusercontent.com/anza-xyz/agave/master/cost-model/src/block_cost_limits.rs) · [SIMD-0207/0256/0286/0306](https://github.com/solana-foundation/solana-improvement-documents/tree/main/proposals)

**Precompile CU costs (from `compute-budget/src/compute_budget.rs`, `COMPUTE_UNIT_TO_US_RATIO=30`):** Ed25519-strict 2,400 CU, secp256k1 6,690 CU, **secp256r1 4,800 CU**, generic tx signature 720 CU, write-lock 300 CU. `enable_secp256r1_precompile` (`srremy31J5Y25FrAApwVb9kZcfXbusYMMsvTK9aWv5q`) is confirmed **activated** (low activation slot, long-standing) via RPC — Warden's root-of-trust precompile is solid ground.

**big_mod_exp is NOT live; SIMD-0529 is "Idea" stage.** RPC confirms feature `expH2ppKPW2ANEdEmAjfhSEcnBQJfmoX4FjuNpe9ttg` is `null` on mainnet. `curve25519_syscall_enabled` and `enable_alt_bn128_syscall` are both confirmed **activated** long ago. **No SIMD-0579 / keccak-p1600 exists** in the SIMD repo as of 2026-08-18 (full proposal listing tops out at 0565-secp256r1-syscalls) — that reference appears fabricated or premature; `sol_keccak256` already exists as an ordinary, long-standing syscall unrelated to any such number. Flag as **UNVERIFIED/likely nonexistent**.

**secp256k1 precompile crate migration is consensus-risky and in-flight.** SIMD-0505/0506 ("Upgrade secp256k1 to k256," Agave-specific, status Review) explicitly calls out fork risk from `libsecp256k1`→`k256` behavioral drift, to be dual-implemented behind a feature gate.

**secp256r1 curve *syscalls* (SIMD-0565, Draft) are separate from the existing sig-verify precompile** — they add group-op/MSM primitives for custom BPF crypto, not a replacement for the precompile Warden already uses.

**Durable nonces: statically-included account is enforced (live); block-failure-on-invalid-nonce is still current behavior.** SIMD-0242 ("Static Nonce Account Only," status **Implemented**) requires `AdvanceNonceAccount` to be the transaction's first instruction and the nonce account to be a statically-listed key (no ALT). SIMD-0297 ("Relax Invalid Nonced Transactions Constraint," status **Review**) would soften an invalid nonce from block-replay-failure to a soft, fee-charged skip — **not yet live**, so an invalid durable-nonce tx still poisons the whole block on replay today.

**Token-2022 has 22 extensions** (per `solana-program/token-2022` `program/src/extension` listing): confidential_{transfer,transfer_fee,mint_burn}, cpi_guard, default_account_state, {group,group_member,metadata}_pointer, interest_bearing_mint, memo_transfer, mint_close_authority, non_transferable, pausable, **permanent_delegate**, **permissioned_burn**, reallocate, scaled_ui_amount, token_group, token_metadata, transfer_fee, transfer_hook, immutable_owner. **Custody-dangerous for a before/after conservation-check adapter**: `permanent_delegate` (mint authority can move/burn *any* holder's tokens — rug vector, must reject or explicitly allowlist), `transfer_hook` (arbitrary attacker/authority-controlled CPI on every transfer), `transfer_fee` (received amount < sent — naive equality checks will false-positive-reject), `confidential_transfer`/`confidential_mint_burn` (amounts are ZK-hidden — **breaks visible-amount conservation checks entirely**), `default_account_state`/`pausable` (can silently freeze funds), `permissioned_burn` (authority-gated forced burn — same rug shape as permanent_delegate). `cpi_guard`/`immutable_owner` are protective, not dangerous. Note: the crate did a v9.1.0 refactor moving extension logic into `spl_token_2022_interface`, deprecating direct `spl_token_2022` re-exports — pin carefully. [dir listing](https://github.com/solana-program/token-2022/tree/main/program/src/extension)

**LiteSVM and Mollusk both under-verify precompiles — a real gap for a passkey wallet's test suite.** LiteSVM's `precompiles` feature is opt-in and its own doc string only claims "ed25519, secp256k1" (secp256r1 unmentioned, though the underlying `agave_precompiles::get_precompiles()` call is feature-gated generically); the loader only installs **stub executable accounts** (native_loader-owned, empty data) — no `verify_precompiles` call exists anywhere in `litesvm/src/lib.rs`. Mollusk's own README states it "does not create any semblance of a validator runtime," and its `instructions_sysvar.rs` **literally serializes whatever instruction list the test author hands it via `construct_instructions_data` with zero independent verification** — a test can assert "secp256r1 verified pubkey X over message Y" into the sysvar without any real P-256 math ever running. **A Mollusk-only (or default-LiteSVM) test suite can pass Warden's introspection logic against a forged signature claim.**

## What Warden should adopt / change

- **Keep designing for 1,232 B / CPI-depth-4 as the hard floor**; do not gate any Phase-1B/1C feature on SIMD-0296/0385/0268 landing — none are activated, and 0296/0385 don't even have feature keys yet.
- **Re-verify the passkey/session-key path against a real validator (solana-test-validator or a fully-configured LiteSVM `with_precompiles()` + explicit `with_sigverify(true)` + manual precompile-instruction-data assertion) at least once per release**, not just Mollusk. Add an explicit CI gate that fails if Instructions-sysvar introspection tests only run under Mollusk.
- **Bind precompile checks to a specific instruction index whose internal offsets you also validate** (message/signature/pubkey offsets must point into the *current* transaction's own bytes at the offsets you expect) — don't just scan for "any secp256r1 instruction present," since a decoy instruction elsewhere in the same tx can satisfy a loose existence check.
- **Extend the (program, discriminator) adapter registry with a Token-2022 extension-awareness layer**: reject/allowlist `permanent_delegate` and `permissioned_burn` mints outright for custody; make the before/after conservation check `transfer_fee`-aware (delta ≥ amount − max_fee, not equality); treat any confidential-extension mint as **out of scope** for automatic conservation checks (can't observe cleartext amounts) — require an explicit user-consent path instead.
- **Track `raise_cpi_nesting_limit_to_8` and `increase_tx_account_lock_limit`-style features via a small on-chain feature-account poller** (the `null`/populated RPC check used above) rather than relying on SIMD status labels, which lag actual cluster activation in both directions.
- Budget CU headroom using the *current* precompile costs (secp256r1 4,800 CU) plus your own instruction costs against the 60M block / 24M per-writable-account ceilings, not the 100M SIMD-0286 figure some docs advertise.
