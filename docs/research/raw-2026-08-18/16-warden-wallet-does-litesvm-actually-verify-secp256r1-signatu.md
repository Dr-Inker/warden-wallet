# Warden Wallet: Does LiteSVM Actually Verify secp256r1 Signatures?

## Findings

**Configuration is correct and non-default-safe.** `programs/warden/Cargo.toml` pins `litesvm = { version = "0.12", features = ["precompiles"] }` as a direct dev-dependency (github.com/Dr-Inker/warden-wallet, commit `a02aaf0`, 2026-08-18) — the `precompiles` feature is **not** LiteSVM's default and must be requested explicitly. `tests/common/mod.rs::setup()` builds the harness as `LiteSVM::new().with_mainnet_features()`. Reading LiteSVM v0.12.0 source directly (github.com/LiteSVM/litesvm, tag `v0.12.0`, `crates/litesvm/src/lib.rs`): `new() = default().into_basic()`, and `into_basic()` unconditionally calls `.with_mainnet_features()` then, gated on `#[cfg(feature="precompiles")]`, `.with_precompiles()`. `MAINNET_ACTIVE_FEATURES` (`features.rs`) includes `agave_feature_set::enable_secp256r1_precompile::ID` (SIMD-0075). Warden's repeated `.with_mainnet_features()` call is redundant but harmless (idempotent, feature-set is read live by the checker, not cached at load time).

**The actual verification path is real, not a stub.** `crates/litesvm/src/callback.rs`: `is_precompile`/`process_precompile` call straight into `agave-precompiles::get_precompile(...).verify(data, &instruction_datas, &feature_set)` — the identical crate/function mainnet-beta validators run, gated only on `feature_set.is_active(&feature_id)`, independent of whether the placeholder executable account was loaded. `message_processor.rs` routes every top-level instruction whose `program_id` is a precompile through this path instead of the BPF loader, and any `Err` becomes `TransactionError::InstructionError`, failing the whole transaction atomically before later instructions run — exactly mainnet semantics. Warden's own `docs/TOOLCHAIN.md:43` and `docs/spikes/DECISION.md:59` independently document this: "`precompiles` is **not** a default feature; without it the secp256r1 precompile account is never loaded and the transaction fails with `InvalidProgramForExecution`" — i.e. the authors already knew this was load-bearing.

**`root_verify/precompile.rs::bind_precompile` explicitly does NOT check the signature.** Its own doc comment: "the signature itself is verified by the runtime, outside this program... The signature bytes themselves are verified by the runtime; we only prove they are present and in bounds." So correctness of Warden's on-chain logic is **entirely contingent** on the SVM actually running real secp256r1 verification upstream of the program — making this exact question load-bearing for wallet security, not academic.

**Empirical test (performed live, this session):** Built the local `/opt/warden` checkout (clean tree, `a02aaf0`) and added a standalone probe test (`programs/warden/tests/forged_sig_probe.rs`, removed after the run — tree left clean). It builds a syntactically valid secp256r1 precompile instruction with the **real** pubkey and **real, honestly-signed message**, but a forged 64-byte signature (`[0x42; 64]`, not derived from the key). Result:
```
PROBE RESULT: tx rejected with: InstructionError(0, Custom(2))
```
`InstructionError(0, ...)` — instruction **0** is the precompile itself, not `rotate_nonce` (instruction 1, which would show `Custom(6000+n)` per the pinned Anchor error table). `Custom(2)` decodes via `solana-precompile-error 3.0.0`'s `PrecompileError` enum (`InvalidPublicKey=0, InvalidRecoveryId=1, InvalidSignature=2, ...`) as **`InvalidSignature`**. This is the runtime's own real ECDSA/P-256 check firing — the transaction never reached `warden::rotate_nonce` at all. Confirms the wiring is genuinely live, not merely configured-and-untested.

**Gap: the shipped test suite never actually exercises this.** `tests/root_verify.rs`'s own header states "Every negative case here is a *real signed assertion* — the passkey signs whatever hostile `clientDataJSON` the case asks for." Verified by reading the full `Case`/`build()` machinery (275–420) and both call sites of `passkey::precompile_ix_custom` (lines 346, 533 of `root_verify.rs`): every one passes `assertion.signature64_low_s`, always the output of `pk.sign(&message)` (`tests/common/passkey.rs`). No test anywhere in `programs/warden/tests/*.rs` (grepped for signature mutation, garbage bytes, random bytes) ever supplies a signature that fails to satisfy the ECDSA equation for its claimed pubkey/message. Every "rejected" case is rejected by Warden's *own* program-level checks (pubkey/message mismatch, index binding, nonce/expiry, clientDataJSON parsing) — none of the 34 tests in `root_verify.rs` would distinguish today's correctly-wired runtime from a hypothetical future regression (dependency bump dropping the `precompiles` feature, a `LiteSVM` version change altering default feature activation, or someone building the harness via a different constructor that skips `.with_precompiles()`/mainnet features) that silently made `bind_precompile` the *only* gate on the root of trust.

## What Warden should adopt / change

1. **Promote the probe to a permanent, first-class test** in `tests/root_verify.rs` (or a new `tests/sigverify_wiring.rs`): forged signature over the real pubkey/message → assert `InstructionError(0, Custom(2))` specifically (not just "any error"), so a regression that changes the failure mode (e.g. falls through to a Warden-level `Custom(6000+n)` because the runtime stopped checking and `bind_precompile` alone caught something else) is distinguished from a genuine sigverify failure. Also add the complementary **positive control**: an honestly-signed assertion for a *different* message than the one bound (`assertion.message` swapped) should still fail via the runtime for a *different* reason — this pins that the harness isn't accidentally rejecting for account/PDA reasons unrelated to crypto.
2. **Assert the harness precondition explicitly**, once, near `setup()`: a smoke test that a syntactically valid secp256r1 instruction with a deliberately-broken signature is rejected with `PrecompileError::InvalidSignature` specifically — failing loudly and immediately (not via a downstream, harder-to-diagnose Anchor error) if a future `Cargo.toml`/LiteSVM bump silently drops real verification.
3. **CI gate**: no `.github/workflows` exist for Warden yet (only inside vendored third-party spike repos). When CI is added, make it run `cargo test -p warden` and treat the sigverify-wiring test's absence-or-failure as a hard build failure — i.e. don't let "tests pass" alone stand in for "passkey path is cryptographically verified"; a CI step that also runs `cargo tree -p litesvm -e features` (or diffs against a pinned lockfile) to positively confirm the `precompiles` feature is still active on the resolved dependency would catch a `Cargo.lock` drift that this test alone might survive by accident if some other precompile stayed enabled.
4. **Minimal harness spec for anyone extending this**: `litesvm = { version = "0.12"–"0.12.x", features = ["precompiles"] }` (0.13+ jumps to Agave 4.x — do not bump without re-verifying this whole chain) + `LiteSVM::new()` or explicit `.with_mainnet_features()` (to activate `enable_secp256r1_precompile`, SIMD-0075) + `.with_precompiles()` reachable (it is, via `new()`'s `into_basic()`). A bare `LiteSVM::default()` without `.with_mainnet_features()` would NOT activate the secp256r1 gate and would misrepresent the runtime as insecure-by-default when it's actually just unconfigured — a real local validator (`solana-test-validator`) needs no such feature flag since `enable_secp256r1_precompile` is already active on all current clusters, but LiteSVM's default `FeatureSet::default()` starts with everything off, which is the actual footgun here.

## Confidence

**High** on the core question (does LiteSVM verify secp256r1 signatures at all): confirmed both by reading LiteSVM's pinned-version source (`agave-precompiles::verify`, real crypto, not a stub) and by a live, reproducible empirical run against the actual local build (`InstructionError(0, Custom(2))` = `PrecompileError::InvalidSignature`, instruction 0 = the precompile, not the program). **High** on the coverage gap (no shipped test exercises a cryptographically-invalid signature) — verified by exhaustive grep/read of every `precompile_ix_custom` call site. **Medium** on the CI-gate recommendation's completeness, since no CI exists yet to evaluate against.
