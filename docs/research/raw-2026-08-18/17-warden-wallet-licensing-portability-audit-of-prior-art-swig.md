# Warden Wallet — Licensing & Portability Audit of Prior Art (Swig, Backpack, LazorKit v2, Squads v4/v5)

## Findings

**Confirmed licenses (verified against each repo's `LICENSE` file and README, Aug 18 2026):**

- **Swig** — `github.com/anagrambuild/swig-wallet`. **AGPL-3.0-only.** No `LICENSE` file at repo root (GitHub's detector returns `null`); license is stated in README's "License" section: "Copyright (C) 2025 Anagram Ltd. This software, Swig, is licensed under the GNU Affero General Public License v3.0." [github.com/anagrambuild/swig-wallet/blob/main/README.md](https://raw.githubusercontent.com/anagrambuild/swig-wallet/main/README.md). Full independent audit PDF (Accretion, 2025) is public in `/audits`.
- **Backpack** — `github.com/coral-xyz/backpack`. **GPL-3.0** (plain GPL, *not* AGPL — confirmed via GitHub API `license.spdx_id: "GPL-3.0"` and raw `LICENSE` text). [github.com/coral-xyz/backpack/blob/master/LICENSE](https://raw.githubusercontent.com/coral-xyz/backpack/master/LICENSE). Backpack ships **no on-chain smart-account program** — it's a client-only xNFT wallet extension; its own README self-labels the code "unaudited... not ready for production," so it's a weaker provenance source than the others even before licensing is considered.
- **LazorKit `program-v2`** — `github.com/lazor-kit/program-v2`. **MIT** (Copyright (c) 2025 LazorKit) — confirmed via `LICENSE` file. [raw LICENSE](https://raw.githubusercontent.com/lazor-kit/program-v2/main/LICENSE). Same for the sibling commercial build `lazor-kit/lazorkit-protocol` (also MIT) and most of the `lazor-kit` org (wallet-adapter is Apache-2.0). Notably its README documents a real precedent for Warden's Jupiter-adapter-fee model: the *same* mainnet program ID is shared between the free `program-v2` build and the fee-taking `lazorkit-protocol` build, with the client SDK probing a `ProtocolConfig` PDA to decide whether to append fee accounts.
- **Squads v4** — `github.com/Squads-Protocol/v4`. **AGPL-3.0**, with a documented exception: two specific utility files (`utils/system.rs`, `utils/small_vec.rs`) are carved out as derived from Apache-2.0 (Anchor) / Apache-2.0+MIT (borsh-rs) code and remain under those permissive terms even though bundled in an otherwise-AGPL repo — stated explicitly in the README License section. [raw LICENSE](https://raw.githubusercontent.com/Squads-Protocol/v4/main/LICENSE). Four public audits (Trail of Bits, OtterSec, Neodyme, Certora formal verification).
- **Squads "v5" / `smart-account-program`** — `github.com/Squads-Protocol/smart-account-program`. Also **AGPL-3.0** per GitHub API license metadata (same org, presumably the successor to v4 under the new "smart account" branding you referenced).

**License-family implication:** three of the four prior-art sources Warden is closest to architecturally (Swig, Squads v4/v5) are **strong copyleft (AGPL-3.0)**; Backpack is **copyleft (GPL-3.0)**; only LazorKit is **permissive (MIT/Apache-2.0)**. Warden Wallet's own repo (`Dr-Inker/warden-wallet`) is **MIT**, Copyright (c) 2026 drinkerlabs — confirmed via `LICENSE` file. [raw LICENSE](https://raw.githubusercontent.com/Dr-Inker/warden-wallet/main/LICENSE).

**Why this matters for a browser extension + on-chain program shipped together:** GPL/AGPL copyleft attaches to the *combined/derivative work*, not per-file. If any AGPL/GPL source is compiled into Warden's Rust program binary or bundled into the extension's JS output, the resulting distributable (the `.so` program and/or the extension package) becomes a "work based on" the covered code under GPL §5/AGPL §13, and the *whole* combined work must be offered under the same (A)GPL terms — this would override Warden's current MIT license for the parts that ship together, not just the copied file. GPL's trigger is **distribution** (extension install = distribution, unambiguous). AGPL additionally triggers on **letting users interact with the program remotely over a network** (AGPL §13) — whether a Solana on-chain program's RPC/transaction-submission interaction with users legally counts as this is **UNVERIFIED / no tested case law**; Warden should not rely on it *not* applying. "Mere aggregation" (GPL FAQ) — independent programs on the same disk/store that don't share address space or get statically linked — does **not** trigger copyleft, but that exception is narrow and doesn't cover copy-pasting logic into your own crate.

## What Warden should adopt / change

- **Freely vendorable, attribution-only:** LazorKit `program-v2` (MIT) is the one repo Warden can literally copy code from — e.g. its odometer-counter replay scheme, session-key action-permission bit-packing, or `CompactInstructions` index-packing pattern — provided the MIT copyright/permission notice is preserved for the copied file(s) (a `THIRD_PARTY_NOTICES.md` entry is sufficient; MIT doesn't require per-file headers). If pulling from `wallet-adapter` (Apache-2.0) instead, additionally retain the Apache header on the modified file and note "changed" per Apache-2.0 §4(b) — Apache content can live inside an otherwise-MIT repo as long as that provenance is preserved; it does not force AGPL-style relicensing of the whole project.
- **Do not vendor Swig or Squads v4/v5 code (AGPL) or Backpack code (GPL) into Warden's program or extension.** Treat them strictly as **design references** — read the source to understand the secp256r1-precompile pattern, session-key bucket accounting, or execute/adapter-registry approach, then have the implementing engineer write Warden's version from a clean design spec without the source open, i.e. genuine clean-room reimplementation. This is exactly what your two-model loop already supports: have Codex's adversarial review pass include an explicit "did this diff copy structure/variable-naming/comments recognizably from Swig/Squads/Backpack" check, since substantial-similarity (not just verbatim copying) can still create derivative-work exposure.
- **The two Squads v4 Apache/MIT-exception files are the one narrow exception** where literal code reuse from the Squads repo is safe (they're independently permissively-licensed, just co-located in an AGPL repo) — but they're generic Anchor/borsh utility code (constraint codegen, small-vec serialization), not core wallet-authority logic, so limited practical value to Warden.
- **Add a `THIRD_PARTY_NOTICES.md` / per-file SPDX ledger now**, before any more prior-art-adjacent code lands, tracking origin + license for every vendored or closely-adapted snippet (including MIT/Apache ones) — cheap insurance and gives Codex's review pass a concrete artifact to check diffs against.
- **Don't reuse names/marks** ("Swig," "Backpack," "Squads," "LazorKit," their logos) regardless of code license — trademark is separate from copyright licensing and none of these grants brand rights.
- **If Warden ever wants literal Swig or Squads functionality rather than a rewrite**, the clean legal path is CPI-calling their *own deployed, unmodified* mainnet program as an external dependency (like calling Jupiter) rather than importing their source — that keeps Warden's program a separate, non-derivative work interacting with an independent AGPL program at arm's length, at the cost of losing control over Warden's bespoke root/authority model, which defeats the actual design goal, so in practice this isn't a real option for the core program.

- Whether `Squads-Protocol/smart-account-program` is officially "v5" (vs. an internal working name) is inferred from repo naming/timing, not confirmed by an official Squads announcement — **UNVERIFIED**.
- Whether Swig's audit PDF being present in-repo supersedes the README's older "shared upon request" language, or whether that's just a stale README, is unconfirmed.

High on the four license identifications and Warden's own MIT status (all verified directly against `LICENSE` files / GitHub API license metadata, not secondary sources). Medium on the AGPL-network-use applicability to on-chain programs (unsettled law, not a fact I can verify) and on the "v5" naming inference.
