# Warden Replay-Design Adjudication: Nonce vs Counter vs Slot Window

## Findings

**Warden's actual mechanism is not a "set."** `verify_root_assertion` (`programs/warden/src/root_verify/mod.rs`) consumes a single `u64 root_nonce` field on the zero-copy `SmartAccount` PDA — incremented by exactly 1 on every successful root ceremony, checked by **strict equality** against the value baked into the signed WebAuthn `challenge` (transcript hash includes `generation`, `policy.version`, `root_nonce`, account key, program id, `cluster_tag`, `expiry_ts`, `action_hash`). [github.com/Dr-Inker/warden-wallet/blob/main/programs/warden/src/root_verify/mod.rs](https://github.com/Dr-Inker/warden-wallet/blob/main/programs/warden/src/root_verify/mod.rs) There is no growing list of consumed values — storage is O(1), zero incremental rent. Freshness is a **client-chosen absolute Unix-time deadline**: `now ≤ expiry_ts ≤ now + MAX_ROOT_EXPIRY_SECS`, with `MAX_ROOT_EXPIRY_SECS = 600` (10 minutes) (`constants.rs`). A dedicated no-op instruction, `rotate_nonce`, exists solely to let a user deliberately invalidate an outstanding signed-but-unsubmitted ceremony by bumping the nonce (`instructions/rotate_nonce.rs`).

**LazorKit (`program-v2`) uses the same scalar-odometer pattern**, not a set: `AuthorityAccountHeader.counter: u32`, `expected_counter = counter.wrapping_add(1)`, strict equality required. Freshness is **slot-relative-to-verification-time**: client signs the current `slot`, program requires `current_slot − slot < MAX_SLOT_AGE` with `MAX_SLOT_AGE = 150` (~60s at 400ms/slot). [github.com/lazor-kit/program-v2/blob/main/program/src/auth/secp256r1/mod.rs](https://github.com/lazor-kit/program-v2/blob/main/program/src/auth/secp256r1/mod.rs) A test (`nonce_integration_tests.rs`) confirms a slot-0 replay attempt at slot 200 is rejected as `InvalidSignatureAge`. LazorKit also has a **deferred-execution path** (`processor/authorize.rs`) with an independently client-chosen expiry (10–9,000 slots, ~4s–1hr) — architecturally closer to Warden's deadline model, but gated behind a separate two-transaction flow, not the default single-shot Execute.

**Swig also uses a scalar odometer, not a set**: `authority.signature_odometer`, `expected_counter = odometer.wrapping_add(1)`, strict equality (`state/src/authority/secp256r1.rs`). Freshness: `MAX_SIGNATURE_AGE_IN_SLOTS = 60` (~24–30s), same slot-relative-to-verification-time model as LazorKit. [github.com/anagrambuild/swig-wallet/blob/main/state/src/authority/secp256r1.rs](https://github.com/anagrambuild/swig-wallet/blob/main/state/src/authority/secp256r1.rs) Comments in both LazorKit and Swig explicitly note the WebAuthn hardware sign-counter is **deliberately not checked** because cloud-synced passkeys can return 0 or non-monotonic values — both projects independently converged on an on-chain program counter as the sole replay guard, corroborating Warden's same choice.

**Convergent design, divergent freshness window.** All three: (1) single fixed-size scalar per authority — no rent growth, no pruning need; (2) strict `n+1` equality — serializes all ops from one authority, which also means reordering of two queued root/root-equivalent ops is structurally impossible (whichever lands first wins). The only material axis of disagreement is freshness: Warden 600s wall-clock deadline vs. LazorKit 150-slot (~60s) vs. Swig 60-slot (~24–30s), both slot-relative-at-verify-time.

## Decision

**Keep the scalar-nonce/strict-equality core (do not change it) — it is already best-in-class among the three and correctly avoids the storage-growth failure mode a literal "consumed-nonce set" would carry.** **Change the freshness mechanism**: replace or supplement the 600s wall-clock `expiry_ts` cap with a slot-relative check, tightened toward the LazorKit/Swig magnitude for anything that isn't an explicitly deferred/timelocked flow.

Rationale: `Clock::unix_timestamp` is a stake-weighted validator estimate, not the tamper-evident quantity `slot` is — every other reviewed wallet anchors freshness to `slot`, and Warden's own root-verify already reads `Clock` only for `unix_timestamp`, forgoing that harder guarantee for no compensating benefit (UNVERIFIED: exact drift/manipulation bound Solana permits on `unix_timestamp`; directionally well-established that slot progression is the more consensus-native clock). The 10-minute window is also 10–25x wider than peers with no stated justification found in the docs — it maximizes the "held signed intent" attack surface (a MITM'd/leaked signed root ceremony — clipboard, malicious relay, compromised dApp iframe — stays replayable for up to 10 minutes) while `rotate_nonce` only helps if the *legitimate* user notices and acts before an attacker submits. A tighter window shrinks that exposure window by an order of magnitude with only a marginal resync-UX cost, since `rotate_nonce`'s design intent (deliberate invalidation) is preserved regardless of window length.

## Failure-mode tests (adjudication matrix)

| Scenario | Warden (current, 600s wall-clock) | LazorKit (150 slot) | Swig (60 slot) | Recommended Warden behavior |
|---|---|---|---|---|
| **Dropped tx** (signed, never lands; blockhash expires) | Resubmit identical payload anytime <10min, no re-prompt. Warden's own test harness (`send_fresh`) proves resubmission across an expired blockhash still succeeds via program-level nonce check, independent of runtime dedup. | Must resubmit within ~60s or re-prompt user for a fresh passkey tap. | Must resubmit within ~24–30s — tightest resync budget of the three. | Adopt a **slot window of ~150–300 slots (~60–120s)**: wide enough to survive one congested-network retry cycle, narrow enough to bound leaked-intent exposure. |
| **Reordered concurrent ops** (two root ops queued, e.g. policy change + revoke) | Structurally impossible: both reference nonce N; only first-landed succeeds, second gets `ChallengeMismatch`/`NonceMismatch` and must re-sign against N+1 (proven by `consecutive_ceremonies_each_consume_one_nonce`, `replay_same_assertion_rejected`). | Identical guarantee via `counter+1` equality. | Identical guarantee via `signature_odometer+1` equality. | No change — this is the correct behavior; do not weaken to a tolerance band (`n` or `n+1` accepted) as that would reopen reordering. |
| **Concurrent multi-device/multi-tab signing** (same synced passkey, two clients race) | Loser gets rejected, must refetch on-chain `root_nonce` and re-sign. No test found for this specific race; recommend adding one. | Same failure mode; not covered by public tests reviewed. | Same failure mode; not covered by public tests reviewed. | Client SDK must **never cache** `root_nonce` locally across a signing ceremony — always re-read immediately before building the challenge. Add an explicit integration test simulating two clients racing on the same nonce. |
| **Intercepted signed-but-unsubmitted ceremony (replay by attacker)** | Valid up to 10 min unless owner calls `rotate_nonce`. Largest exposure window of the three. | Valid up to ~60s. | Valid up to ~24–30s. | Shrink window per Decision above; also surface a "pending signature" UI affordance that auto-suggests `rotate_nonce` if a signed-but-unconfirmed ceremony is abandoned. |
| **Cross-device passkey use (iCloud/Google sync)** | No per-device sub-counter; global `root_nonce` serializes all devices — same as peers. Comment in LazorKit/Swig confirms this is why the WebAuthn hardware counter is ignored industry-wide. | Same. | Same. | No change — this is the correct converged design; do not attempt per-device counters, which would fragment the replay guarantee. |
| **Storage/rent growth over account lifetime** | O(1): fixed 8-byte field in the existing ~4KB PDA, zero incremental rent regardless of tx volume. | O(1): fixed 4-byte field in 48-byte header. | O(1): fixed field in Authority account. | No change — all three already avoid the growing-set anti-pattern; confirm this explicitly in Warden's docs since the "consumed-nonce set" phrasing in the spec is misleading and should be corrected to "nonce" or "odometer." |

## What Warden should adopt / change
1. **Add a slot-relative freshness check** (`current_slot − signed_slot < N`, N ≈ 150–300) in addition to or instead of the 600s wall-clock `expiry_ts`; keep `expiry_ts` only for the already-separate timelocked/large-move flow where a longer, client-visible deadline is a legitimate feature, not an implicit side effect of the default path.
2. **Rename "consumed-nonce set" in specs/docs to "nonce"/"odometer"** — the current term invites reviewers (and future engineers) to assume O(n) storage/rent growth that doesn't exist; precision here prevents a wasted future "fix."
3. **Add an explicit concurrent-signer race test** (two ceremonies built against the same on-chain `root_nonce`, submit both) mirroring LazorKit's `nonce_integration_tests.rs` style, to lock in the reject-loser/no-double-consume guarantee Warden's other tests already imply but don't directly exercise for the multi-device case.
4. **Surface `rotate_nonce` in wallet UX** as a user-facing "cancel pending approval" action rather than leaving it as an internal-only escape hatch, since a wide freshness window makes proactive invalidation the primary mitigation against leaked intents.

## Open questions

## Confidence
High confidence on the source-code claims (all three replay mechanisms read directly from primary-source raw files, commit `main` as of 2026-08-18, with the specific line-level constants (`600`, `150`, `60`) and test names cited). Medium confidence on the Decision's slot-vs-timestamp security framing (directionally standard, not independently proven against Warden's specific threat model) and on cross-repo comparability (LazorKit/Swig are pre-audit-disclosure or partially-audited third-party repos, not verified against a security audit in this pass — Swig repo states an Accretion audit exists "upon request," not fetched here).
