# Warden Rust Review-Loop A/B: Does the +18.1/-8.6pp Asymmetry Hold at Repo Scale?

## Method (executed this session, primary data)
Warden's loop is **structurally one-directional**: `CLAUDE.md` mandates "every task is implemented by [Claude] and adversarially reviewed by Codex" (`/opt/warden/CLAUDE.md`) — there is no historical Codex-authors/Claude-reviews data in this repo to mine. So I ran three real, executed probes instead of a literature-only answer:

1. **Historical audit** of `git log` on `programs/warden/` (10,536 LOC, pure Anchor — no Pinocchio anywhere in the repo; `grep -ri pinocchio` returns nothing) — the actual Codex-reviews-Claude findings ledger, as committed.
2. **Live blind Codex review** (`mcp__codex__codex`, `gpt-5.6-terra@high`, fresh thread `01a016ba`) of the current `create_account.rs` (573 lines), scoped to that one file.
3. **Live reverse-direction pilot**: Codex (`01a016bb`) authored a new, self-contained 30-day ring-buffer spend function (`spend_bucket`, matching Warden's real `MintBuckets` schema) from a written spec; I reviewed it blind, then **compiled and ran it** to confirm findings empirically rather than by inspection alone.

## Findings

- **Historical ledger (Codex→Claude, 4 real review rounds, this repo):** 1 Critical, 4 Important, 6 Minor findings, **100% adopted** — session `per_day`/`per_30d` caps stored-but-never-enforced (Critical, `9217b6a`); unbound re-grant authority, unusable-root creation, unassigned ops-mask bits (3 Important, `b59d2ce`); unbound `program_allowlist_id` and an unbound revoke-refund rent-drain (`a25486a`). No round records a *disputed/rejected* Codex finding anywhere in `docs/spikes/PHASE1A-LEDGER.md` or the commits — the 100% adoption rate is a **survivorship-biased artifact of what gets committed**, not evidence Codex's false-positive rate is 0%.
- **A real regression, caught cross-round (not cross-model):** `b59d2ce`'s fix for the P-256 root-key check over-corrected and rejected `x=0`, which is a valid P-256 point — a genuine security regression shipped between review rounds, caught by a *second* Codex round (`4b409f7`, thread `01a0164f`: "the first fix pass rejected it wrongly"). This is real regression-introduction/catch data, but both ends are Codex — it says nothing about Claude-catches-Codex-regressions.
- **Live single-file Codex review (probe 2) produced one finding**, technically correct but scope-blind: it flagged `cluster_tag` binding (`create_account.rs:88,121`) as an unaddressed Important cross-cluster-replay gap. But `root_verify/transcript.rs:69-76` *already documents this exact property* as a known, non-cryptographic, client-attested domain separator, explicitly deferred to "Task 9." Codex wasn't shown that file. Scored against my instruction ("don't restate known/deferred issues"), this is a **false positive driven by review scope, not model identity** — the same failure mode would likely hit a Claude reviewer given only one file.
- **Live reverse-direction probe (probe 3) produced one confirmed true positive**, verified by execution, not inspection: Codex's `spend_bucket` writes the just-closed day's spend into `ring[kept-1]` instead of `ring[RING_DAYS-1]` during a partial rollover. I compiled the file and ran a two-day scenario (spend 100 on day 0, 50 on day 1): `ring[28]=100, ring[29]=0` — the correct slot is permanently zero and one day's history is silently clobbered every rollover. Net effect: the 30-day trailing sum **understates real spend forever**, weakening (not strengthening) the account-wide 30-day cap — a genuine, security-relevant, cap-bypass-direction bug in Codex-authored code, caught by Claude review on the first pass. Separately, the same function sums all 30 ring slots *plus* `spent_today`, covering 31 calendar days against a "30-day" cap — Minor, conservative-direction, not exploitable.
- I could not locate the source of the cited **+18.1/-8.6pp** figure anywhere in this session (`~/.claude/ROUTING.md`, `scorecard.jsonl`, `/opt/docs/`) — it is **UNVERIFIED** as to definition (TP-rate delta? bug-catch-rate-per-LOC? what denominator?), so I cannot check metric parity with what I measured here.

## What Warden should adopt / change

1. **Stop treating 100% Codex-finding adoption as an FP-rate=0 proxy.** Log every finding a round produces, including ones the implementer disputes or scopes out, with adjudication rationale, in a `REVIEW-LEDGER.md` — the current ledger structurally cannot answer "how often is Codex wrong," and that's the exact question this follow-up needs.
2. **Do not restructure the loop into Claude-reviews-Codex or both-directions off this session's n=1-per-direction pilot** — it's real but far too small to set policy. Instead, run a proper matched-pairs pilot across ~10-15 upcoming Phase 1B sub-tasks (execute/adapter-registry/swap have plenty of function-scale surface like `spend_bucket`): each small scope reviewed by Claude, by Codex, and by both, blind, scored against a fixed third-party (or human) adjudication — not the two-model loop's own self-reported commit messages.
3. **Fix reviewer scope, independent of which model reviews.** My probe-2 false positive was caused by handing the reviewer one file when the governing invariant lived in a sibling module (`root_verify/transcript.rs`). Cheap, concrete change: `developer-instructions` for every review round should name the 2-3 sibling files that carry cross-cutting invariants (session state, transcript, errors) before the reviewer is allowed to file a finding against a caller.
4. **Add a second-round confirm specifically for accept/reject boundary changes** (not all diffs) — the one real regression found here (`x=0`) was exactly this shape: a fix that moved a validation boundary. Boundary-condition diffs are cheap to re-review and this repo has already shipped one live miss of that class.
5. **Do not extrapolate the Python-task figure onto Anchor decisions.** This codebase's bugs so far cluster around cross-file invariants and dense inline security rationale (spec citations, deferred-risk notes) rather than isolated logic errors — a different error surface than an isolated script, and probe 2 shows the *reviewer's context window*, not the model, may dominate FP rate here.

## Confidence
**High** that the current ledger cannot answer the asymmetry question as instrumented (one-directional loop, adoption-only logging, no FP tracking). **Low** on whether the cited figure holds or fails at Anchor repo-scale — the real, executed n=1-per-direction pilot here is consistent with real bugs and real reviewer-scope-driven false positives existing on **both** sides, but is far too small to confirm, refute, or replace the Python-task estimate.
