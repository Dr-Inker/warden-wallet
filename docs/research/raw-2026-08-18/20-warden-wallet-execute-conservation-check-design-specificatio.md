# Warden Wallet: Execute/Conservation-Check Design Specification (Pre-Implementation Review)

## Findings

**Status confirmed unbuilt, but already substantially specified.** `execute` is not merged — it's scoped for Phase 1B (Phase 1A merged: `create_account`, `transfer`, session caps, 292 Rust + 50 TS tests). Design lives in `docs/superpowers/specs/2026-08-18-warden-wallet-design.md` §5.2.2/§5.3 and `docs/superpowers/plans/2026-08-18-warden-phase1b-execute-swap.md` on [github.com/Dr-Inker/warden-wallet](https://github.com/Dr-Inker/warden-wallet).

**Multi-mint / lamport coverage — already specified, sound.** Outflow is computed per-mint as `Σ(amount_before − amount_after)` across all vault-owned token accounts of that mint, floored at 0, then coalesced once before a single `buckets::debit`. SOL is handled separately and correctly to avoid WSOL double-counting: `outflow[SOL] = (pda_lamports_before − pda_lamports_after) + Σ_WSOL(amount_before − amount_after)`; WSOL *token-account lamports* are explicitly excluded from the sum (design spec §5.2.2). This is the right shape.

**Post-CPI re-verification — partial, with a real gap.** The spec snapshots "existence, owner program, lamports, data length" plus, for token *accounts*, `(mint, owner, amount, delegate, delegated_amount, close_authority, state, is_native)` and a Token-2022 TLV hash, enforcing byte-identity on everything but `amount`. This is a legitimate primary-source pattern — Solana's own **Token-2022 CPI Guard extension** does the analogous thing at the token-program layer: when enabled and `in_cpi()==true`, it forces Transfer/Burn signer==delegate, **prohibits Approve outright**, requires CloseAccount's lamport destination == account owner, prohibits SetCloseAuthority unless unsetting, and **always** prohibits SetOwner ([solana-program.com/docs/token-2022/extensions](https://www.solana-program.com/docs/token-2022/extensions); processor source at [github.com/solana-program/token-2022](https://github.com/solana-program/token-2022/blob/main/program/src/extension/cpi_guard/processor.rs)). Warden's design converges on the same invariants independently but does so entirely as a *post-hoc field comparison*, not a proactive instruction-level block — and it doesn't say whether **Mint** accounts (mint_authority, freeze_authority, TransferFeeConfig authorities) get the same snapshot-and-compare treatment as token *accounts*. If a vault ever holds mint authority (e.g., a vault-created LP/reward mint), nothing in the described fields catches a CPI'd `SetAuthority` on that mint.

**Gross-vs-net caps — net-only, and it has a wash-trade blind spot.** Both per-tx/lifetime (per-session) and day/30-day (account-wide) caps debit the *net* outflow figure above. Net accounting is correct for legitimate swaps (input coalesced across legs) but means a session key with adapter access to a DEX can round-trip mint X → Y → X within one `execute` (or across many) and register near-zero net debit each time while bleeding real value to slippage/fees on every loop — never touching the per-tx, day, or 30-day ceilings, because those ceilings are all computed from the same net figure. Design spec §5.3 already flags a related, narrower gap: snapshots "cannot verify external program logic" for positions the vault holds inside a protocol — the wash-trade case is the fungible-token analogue of the same blind spot.

**Token-2022 extension policy — well specified.** Mint-level danger extensions (transfer-hook=14, permanent-delegate=12, confidential-transfer-mint=4) are denied unless policy-allow-listed; account-level extensions (transfer-hook-account=15, confidential=5) are folded into the TLV hash so any post-CPI mutation is caught; a present T22 mint is required whenever a vault ATA of that mint is writable. TransferFeeConfig fields aren't named separately but are covered generically by the TLV-hash-changed rejection — sound, though rebasing/interest-bearing "display-only" extensions may need an explicit carve-out so legitimate non-mutating accrual doesn't false-positive a reject.

**No program-level deny-list for SetAuthority/Approve/CloseAccount is specified anywhere.** The design relies entirely on post-state invariants (`delegate == None`, `close_authority == None` after execution) to make these instructions harmless *in effect*. That differs materially from CPI Guard's approach of blocking the instruction at parse time, and from Squads v4, which performs **no conservation checks and no program allowlist at all** — `vault_transaction_execute` trusts multisig approval alone, with no balance/state validation before or after CPI ([github.com/Squads-Protocol/v4](https://github.com/Squads-Protocol/v4/blob/main/programs/squads_multisig_program/src/instructions/vault_transaction_execute.rs)), confirming Warden's conservation-check ambition is already ahead of the leading comparable primitive — but the specific deny-list requested here is still missing.

## What Warden should adopt / change

1. **Hard-code, don't allowlist-govern, the deny-list.** Reject inner instructions targeting the Token/Token-2022 program IDs with discriminators `SetAuthority(6)`, `Approve(4)`, `ApproveChecked(13)` unconditionally, and `CloseAccount(9)` unless the lamport-destination account index resolves to the vault PDA (index 0) — mirroring CPI Guard's CloseAccount rule exactly rather than only catching a bad destination via lamport-delta accounting after the fact. This must live in the fixed ABI-decode path, not the adapter registry, since the spec states "policy loosening extends it, tightening does not" — a deny that can only be loosened by a future policy version is not a real floor. Apply it identically on the root path (root has dedicated authority-change instructions; `execute` has no legitimate reason to carry SetAuthority).
2. **Extend the snapshot set to Mint accounts explicitly**, comparing `mint_authority`, `freeze_authority`, and (for T22) `TransferFeeConfig` authorities byte-for-byte, whenever a mint the vault has authority over is touched writable. Treat any mint-authority field as an instruction-reject, not merely a rejected-if-noticed accounting entry.
3. **Add a supplementary gross-turnover bucket**, independent of the net-outflow caps, summing absolute value moved per mint per session per day, with its own (looser) ceiling — closing the wash-trade/fee-bleed griefing path without breaking legitimate net-based swap accounting.
4. **Fold non-WSOL rent lamports into the SOL outflow sum on CloseAccount.** As specified, only PDA lamports and WSOL token-account amounts are counted; a CloseAccount on a zero-balance USDC ATA redirecting ~0.002 SOL rent to a non-vault address is currently invisible to both the mint-outflow and SOL-outflow accounting — a slow, uncapped drain. This closes automatically if recommendation 1 is adopted (CloseAccount destination pinned to the PDA), but should be caught by accounting too, as defense in depth.

## Open questions

- Are Mint accounts in scope for the writable-account snapshot set at all in the current draft, or only token *accounts*? The fetched text does not resolve this.
- Should the gross-turnover bucket share the account-wide day/30-day buckets or be a wholly separate cap axis?
- Does `stage_finalize`'s generation/policy_version pinning interact safely with a hard-coded (non-policy) deny-list, or could a stale staged payload attempt to reference a discriminator that policy tightening removed from the *registry* but the hard deny never permitted anyway?

## Confidence

High that the described gaps (mint-authority snapshot, hard-coded deny-list, gross-turnover cap, non-WSOL rent leak) are real and additive, given direct comparison to Token-2022 CPI Guard's proven instruction set and Squads v4's weaker baseline. Medium on exact discriminator values (Approve=4/ApproveChecked=13/SetAuthority=6/CloseAccount=9 are standard SPL Token layout, UNVERIFIED against the Warden repo's own constants since Phase 1B code doesn't exist yet to check against).
