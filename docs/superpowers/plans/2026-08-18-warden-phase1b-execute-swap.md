## Global Constraints

- **Runtime facts that bind, RPC-verified 2026-08-18 (do not design past them).** **CPI depth is 4** — a hard floor, not a target: `execute` is depth 1, its inner instruction depth 2, and anything that program calls depth 3, leaving exactly one level of slack. Plan every adapter against depth 4 and treat a transfer-hook mint (which spends a level mid-transfer) as the reason it is denied outright (spec §5.2 rule 5). Transaction packet **1,232 B**. The **secp256r1 precompile costs 4,800 CU** and must be budgeted explicitly in every root-path CU figure recorded in PHASE1B-MEASUREMENTS.md. **SIMD-0268 ("depth 8") is NOT activated** — its feature account is `null`, not even queued — and SIMD-0296/0385 have no feature keys; **no task in this plan may assume depth 8 or a 4,096-byte transaction.** Poll feature accounts, never SIMD labels or docs.
- **Fixed deny-list, above and outside the registry (spec §5.2 rule 1a).** Enforced in the **payload decoder** (Task 5), on **both** the session and the root path, before dispatch and before any registry lookup: SPL Token and Token-2022 `SetAuthority`(6), `Approve`(4), `ApproveChecked`(13), `Revoke`(5) unconditionally; `CloseAccount`(9) **rejected except for the single vault-sweep case** — a **direct** SPL/T22 `CloseAccount` inner instruction of the payload (account order `[0] account, [1] destination, [2] authority`) whose target has `amount_before == 0` and whose **decoded destination is the SmartAccount PDA**. **A close nested inside another program's CPI is never exempt** — the decoder cannot see it, so it cannot establish those conditions, and it falls through to the conservation comparison, which rejects the unexplained disappearance (spec §5.2 rules 1a/2/3). The decoder emits a **decoded close intent** `{account, destination, amount_before}` per permitted close and hands it to `compare_and_account`; **nothing downstream may infer a close from a disappearance.** **Tags are UNVERIFIED and must be re-derived from the pinned `spl-token` crate's `TokenInstruction` enum**, with the crate version + source path recorded and a unit test asserting each constant. No registry entry may re-enable a denied pair.
- Everything in Phase 1A's Global Constraints still applies (checked arithmetic + clippy deny; authorize-then-validate; PDAs re-derived; `frozen` gates all outflow; tx-size assertions on every new instruction; pinned literal error codes appended 6036+ with the drift-guard test extended; RED evidence per task; serialized builds; commit trailer; Codex reviews every task at **`gpt-5.6-sol` @ `max`**).
- **Conservation is before/after, field-by-field, on every writable account in the instruction** (spec §5.2 rule 2/3/4): for token accounts `(mint, owner, amount, delegate, delegated_amount, close_authority, state, is_native)` + Token-2022 TLV hash; runtime owner program, lamports, data_len for all. Vault-owned token accounts: no field but `amount` may change, `amount` may only decrease by what the session/root is allowed, closed/realloc'd ⇒ reject. The SmartAccount PDA is never writable to a CPI target. Non-token vault-owned writable accounts ⇒ reject. Value accounting per §5.2.4 incl. the SOL equation `(pda_lamports_before − after) + Σ vault-NATIVE-account lamport decreases` (native value is LAMPORTS not the `amount` cache — WRDF-0011); no rent exemption; outer payer funds creation.
- **Session `execute` may CPI only to registry entries `(program_id, discriminator)`** in its list; **self-CPI into warden is rejected**; ComputeBudget program is rejected inside `execute` (must be top-level); **Token-2022 splits three ways and the halves are not symmetric (spec §5.2 rule 5):** `transfer_hook` and `permanent_delegate` are **deny, never allow-listable** — no policy path enables them, in 1C or ever; `transfer_fee` is the **only** allow-listable class and its 1C check is `delta ≥ amount − max_fee`; **confidential-transfer mints are a PERMANENT non-goal** (§13), not a deferred toggle, because conservation over ZK-hidden amounts is unverifiable rather than merely expensive. **1B rejects all three** — that is a tightening of the same rule, not a different rule.
- **`execute` outflow debits the same account-wide buckets** as `transfer` (session: per_tx + lifetime + account buckets; root: large_threshold + account buckets); a mint with no cap ⇒ outflow must be 0. **Outflow is coalesced per mint across all vault token accounts of that mint before ONE `buckets::debit`** (multiple ATAs of the same mint cannot split a per-tx check); SOL = PDA lamport decrease + Σ vault-NATIVE-account **lamport** decreases (not `amount` — WRDF-0011), merged exactly once. Token-2022 dangerous extensions are decided by inspecting the **mint's** TLV (transfer-hook 14, permanent-delegate 12, confidential-transfer mint 4) — the mint account must therefore be present in the tx for any T22 vault token account touched, else reject; token-account-side counterparts (e.g. transfer-hook-account 15, confidential 5) are hashed as part of the account TLV.
- **Mints are snapshotted, and the presence rule generalises to classic SPL (spec §5.2 rule 2a).** Whenever a **vault-owned token account of mint M is writable**, **M's mint account must be present in the transaction**, else reject — for classic SPL as well as Token-2022, which merely widens the T22 requirement above. If the vault holds **any** authority on M (`mint_authority`, `freeze_authority`, or T22 `transfer_fee_config_authority` / `withdraw_withheld_authority`), M is snapshotted before **and** after and every authority field compared **byte-for-byte**; any change is an **instruction reject** (`ConservationViolated`), never an accounting entry. Classic mint = fixed **82-byte** layout, strict COption decoding (`0`/`1` only). T22 mint = the same 82-byte base **plus a TLV tail**, from which the fee authorities are **extracted by TLV type**, not covered by a whole-tail hash — a legitimate `transfer_fee` accrual mutates the tail and a tail hash would false-positive on the happy path. `supply` is snapshotted but is **not** an authority field and is not by itself a reject.
- **Account ABI — payload indices are LOGICAL; ONE canonical mapping, identical in spec §5.2, this section, Task 5 and Task 8 (TS):**
  ```
  logical[0]   = smart_account            // the SmartAccount PDA
  logical[1]   = signer                   // session key, or the payer on the root path
  logical[2+k] = remaining_accounts[k]    // dApp accounts, client order
  ```
  `execute`'s Anchor context has NAMED accounts `smart_account`, `signer`, `session: Option`, `ix_sysvar: Option`, `stage: Option`, `registry: Option` — **all of which sit physically BEFORE `remaining_accounts`, and the optionals make the physical offset of `remaining_accounts[0]` vary.** So the handler **constructs the logical list** (`[smart_account, signer] ++ remaining_accounts`) and indexes *that*; **no code path may index the raw physical account slice, and no payload index ever denotes a physical slot.** `accounts_hash` is computed over the **logical list in logical order** (`pubkey ‖ is_signer ‖ is_writable` per entry), and Task 8's TS decompile-parity check reconstructs the logical list exactly the way the handler does before comparing. `remaining_accounts` = the dApp accounts, in client order. **Payload contract**: `ExecutePayload { n_ixs: u8, ixs: [ { program_idx: u8, n_accts: u8, accts: [(idx: u8, flags: u8 /*bit0 signer, bit1 writable; other bits ⇒ reject*/)], data_len: u16 LE, data } ] }`; `program_idx` must point at an executable account whose key ≠ warden id and ≠ ComputeBudget; **the SmartAccount PDA may never be passed writable to a CPI** (flags bit1 on idx 0 ⇒ reject) — read-only is fine; a `signer` flag is honoured only for `[0]` (PDA via `invoke_signed`) and `[1]`; any other signer flag ⇒ reject; duplicate `(idx)` within one inner ix ⇒ reject; indices out of range ⇒ reject; **the warden program id may not appear anywhere in the remaining accounts** (blocks indirect re-entry via a middleman program); ComputeBudget program id may not appear either. **Snapshot scope (settled — this wording governs; anywhere else in this plan that says "all writable" means this)**: **every `remaining_account`, writable or not** (read-only accounts can still be vault-owned, and the extra cost is cheap insurance) **plus the SmartAccount PDA's own lamports**, tracked separately for the SOL equation, **plus the Mint accounts required by the presence rule below**. Cross-language vector: `packages/core` encodes a payload+accounts fixture that a Rust unit test decodes and re-hashes (accounts_hash) byte-for-byte.
- **Stage accounts**: PDA `["stage", account, hash]`, content-addressed (`hash = Keccak256(payload)`), chunk-uploaded, `finalize` verifies the hash and records `generation` + `policy_version` + `expiry_ts`, consume-once (closed by `execute`), anyone may close after expiry (rent to `creator`). Account layout for `stage_chunk` exactly as spec §5.1.

### Task 0: L0 harness-fidelity gate + slot-freshness transcript change + spec rulings for 1B (before every other task)

**The adapter-decoded source limit — this is 1B's answer to the intra-CPI blind spot, and it is the reason `gross_turnover` was withdrawn (spec §5.2 rule 4b).** A before/after snapshot measures what a CPI *left behind*, not what it *moved*: a route that takes 100 SOL out and returns 99.5 within its own execution nets to 0.5, and no snapshot granularity sees the 100. So the swap adapter does not rely on the net diff alone. **Before the CPI runs**, it must:
1. **Decode `in_amount` / `max_in` out of the inner instruction's own data** — the value the program *read* from the bytes it is about to invoke, not a value inferred from balances afterwards — and check it against the session's `per_tx[in_mint]`, `lifetime`, and the account-wide buckets. A route whose declared input exceeds the cap is rejected **before** any CPI, not diagnosed after.
2. **Pin the source token account.** The role validator requires the inner instruction's `user_source_token_account` to be **exactly the vault ATA of `in_mint` that the caller declared**, and `user_transfer_authority` to be the PDA. The value at risk in the call is then bounded by an account the program **named**, not by whatever the route happens to touch.
3. The net before/after check still runs afterwards and still applies — the two are redundant on purpose. `max_in` bounds authorised input; the net diff bounds realised outflow; **neither is allowed to be the only control**, and the debit is taken on the net diff so an honest partial fill is not overcharged.

**Say plainly in the code comment and in PHASE1B-MEASUREMENTS.md that this is a design bet, not a proven property** (research §4 item 15). It bounds the value the program can see being authorised; it does not close the blind spot, because nothing closes it.

**Why (campaign plan 2026-08-20 G11):** Task 11 landed the deployment gate as

- [ ] **Upgrade-governance check (WRDF-0017, `WRD-DEP-01`), the load-bearing one.**
  Comparing `ProgramData.upgrade_authority_address` against an operator-supplied
  "expected authority" and *separately* checking that some 3-of-5 multisig is
  healthy is **insufficient** — an operator can pass a single-key authority as
  "expected" plus an unrelated healthy multisig and get a false green while one
  key keeps arbitrary upgrade power. Instead: pin the Squads program id and vault
  index; owner-check and decode the multisig; **derive its canonical vault PDA
  from the decoded multisig**; and require `ProgramData.upgrade_authority_address
  == that derived vault PDA`. Then assert the multisig's threshold and time-lock
  match spec §5.5 (3-of-5, 7 days). Never accept the authority and the multisig as
  independent facts.
- [ ] Assert the on-chain program hash equals `solana-verify get-program-hash` of
  the release artifact; **refuse on any mismatch**.
- [ ] **The checks must be explicit assertions, and each must have a valid-looking
  negative fixture that would pass a lazy implementation (WRDF-0017).** Assert, by
  name: the multisig account's **owner == the pinned Squads program id** and its
  **discriminator**; **member_count == 5** (not merely `threshold == 3`); the
  **pinned vault index**; and the **canonical vault PDA seed derivation**. A
  checker that decodes spoofed bytes without the owner/discriminator check, or
  hard-codes one vault index, or checks `threshold == 3` while ignoring
  `member_count`, must FAIL a fixture — so add one negative fixture each: wrong
  account owner, wrong discriminator, `member_count != 5`, wrong vault index, and
  a spoofed non-Squads account whose bytes merely look like a healthy multisig.
- [ ] Deterministic pass/fail fixtures — recorded RPC responses (happy path plus
  each mismatch class above, plus authority ≠ derived vault PDA, single-key
  authority + a healthy but unrelated multisig, wrong threshold, wrong timelock,
  wrong hash, missing account, and RPC error ⇒ **fail closed**) driven through the
  same code path via a `--fixtures` flag; **no network in CI**.
