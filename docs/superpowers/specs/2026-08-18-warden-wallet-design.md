## 1. Purpose and the one property we promise

A Solana browser-extension wallet that is **more secure than Phantom against the losses that actually happen** — AI-scale phishing, fake dApps, drainers, seed-phrase scraping, poisoned addresses, prompt-injected agents — by moving safety from *warnings the user can click through* to **limits the chain enforces**. It keeps the Phantom core: connect to dApps, send, receive, and an in-app Jupiter swap that earns a platform fee.

**The property (stated exactly, because it is the product):** *If an attacker obtains everything the extension holds while unlocked — the session key, the unlocked keyring, the ability to prompt the user — the value that can leave the account before the owner or a guardian can react is bounded by the account's session caps; anything larger is delayed and cancellable.* Bounded means **token/lamport value leaving the account's own token accounts and lamport balance**. It does **not** cover value the user has already placed under other programs' control (see §5.3) or a compromised OS that can defeat the passkey ceremony.

## 2. Threat model

| # | Threat | v1 answer |
|---|---|---|
| T1 | User is talked into approving a draining tx (fake dApp, deepfake support, poisoned address) | Session key: ≤ per-tx and ≤ daily caps per mint, account-wide across all sessions. Larger outflows — **including by the root** — go through a timelock with a cancel window and notifications |
| T2 | Seed phrase scraped | No seed phrase exists in the default path; the recovery code is a 128-bit code that unlocks a *guardian key*, which cannot move funds and is itself subject to the recovery delay |
| T3 | Malicious/updated extension | Root = **non-exportable P-256 passkey verified on-chain**; the extension never holds root secret material. A malicious extension can spend the session caps, and can *ask* the user to complete a passkey ceremony for a large action — that action is still timelocked and visible on the notifier/second device. Explicitly **not** defended: a malicious extension that lies about intent to a user with no second channel |
| T4 | Device/passkey lost | Guardian recovery (threshold, delayed, root-contestable) or the recovery-key path (also delayed) |
| T5 | AI agent/bot with wallet access is prompt-injected | Agents get their own session key with tiny caps (on-chain in v1; UI in v1.1) |
| T6 | Bug in our program | Small typed surface, adversarial + property tests, external audit and bug bounty **before any real funds**, per-account `frozen`, upgrade path with a 7-day lock and an exit window (§5.5) |
| T7 | **Synced-passkey extraction / assertion forgery from a compromised endpoint** | Three attacks disclosed in 2026 — SpecterOps' Entra passkey-registration replay, Unit 42's recovery of the Chrome Security Domain Secret (which yields *every* synced Google Password Manager passkey), and a Windows Hello session-hijack — mean a compromised endpoint can produce assertions without a fresh biometric. `userVerification: required` is mandatory here (§4) and raises the bar, but **does not eliminate the class**: UV is asserted by the authenticator, and a hijacked authenticator session asserts it too. Warden's answer is therefore defence in depth, not passkey purity — the account-wide day/30-day buckets bound what a forged root ceremony extracts (§5.2.4), a timelock + notifier makes anything larger visible and cancellable, and guardians can freeze. **Open owner decision, carried into 1C:** whether a *synced* (multi-device, cloud-backed) passkey may be a root at all, or whether roots must be device-bound (`authenticatorAttachment: "platform"` + no cloud backup flag), with synced credentials permitted only as guardians. Detection of a *cloned* credential via the WebAuthn sign counter is explicitly rejected (§3(e) of the research: synced authenticators return 0 or non-monotonic counters; LazorKit and Swig both ignore it) |
| — | Quantum signature forgery | Out of scope. Preserved: asset holder is a PDA; root/guardian kinds are typed → a hash-based/Falcon kind is additive |
| — | Compromised OS/keylogger with unlocked session | Bounded by caps only |
| — | Lying RPC | Cannot sign; can hide state. Intent view cross-checks simulation vs local pre-check and flags disagreement; user-selectable RPC |

## 4. Key model

**Root = passkey (default).** A platform passkey created from the extension's origin (RP ID = extension id), `userVerification: required`, algorithm restricted to ES256. The P-256 public key is the account root. **On-chain verification:** the secp256r1 precompile (SIMD-0075) is a *transaction-level* instruction and cannot be CPI'd, so the root instruction introspects the Instructions sysvar and requires a secp256r1 instruction **in the same transaction** whose `(pubkey, message, signature)` exactly equal `(root.pubkey, authenticatorData ‖ SHA256(clientDataJSON), sig)`; the program then parses `authenticatorData` (`rpIdHash` == the account's stored expected hash, UP+UV set) and `clientDataJSON` (per the strict scanner below).

**`rpIdHash` is SHA-256 of the FULL extension origin string** — `SHA-256("chrome-extension://<id>")`, **not** `SHA-256("<id>")` (measured, spike 2b, `docs/spikes/DECISION.md` §"Spike 2b"). For the spike's dev-loaded extension: signed `authenticatorData[0..32]` = `be5c4af7cba9d9360e094797024b5a3a3dd9f437aa9852291656e7b5b5d9da34` = `SHA-256("chrome-extension://maikadpaobbjkmaomnpnhjglpabllaoi")`; `SHA-256("maikadpaobbjkmaomnpnhjglpabllaoi")` = `68dd094e7a73750c0036e8a840b1bc086208d82ebb86e13320879d995a2cf051`, which does **not** match. The naive reading of the WebAuthn spec ("rpIdHash = SHA-256(RP ID)", RP ID = the extension id) therefore rejects **every** assertion. Do not conflate the two: the credential request's `rp.id` **is** the bare extension id; what the authenticator *signs* is the hash of the full origin. Because the extension id changes between a dev-loaded and a store-published build, the expected hash is **per-build configuration stored in `SmartAccount` state at account creation and read from state on every verification** — never a compiled-in literal, and never taken from caller-supplied instruction data.

**Low-S normalization is mandatory client-side.** The secp256r1 precompile rejects high-S signatures (`PrecompileError::InvalidSignature`), and Chrome's authenticator emitted a high-S signature on the very first real sample. The extension MUST normalize S on every assertion before submission; the program does not (and cannot cheaply) repair it.

**`clientDataJSON` verification = strict top-level scanner.** Byte-substring matching is **forbidden** (it accepts a nested or duplicated `origin` and falsely rejects legal JSON escapes — demonstrated by executable tests in spike 2b). "Strict" means, exactly: (a) reject before parsing if `clientDataJSON` exceeds a hard length cap (`MAX_CLIENT_DATA_LEN`, 512 B in v1); (b) walk the object at **depth 0 only** — keys inside nested objects/arrays are never considered; (c) require **exactly one** top-level `type`, `challenge` and `origin` key, and reject on any duplicate top-level key rather than resolving it; (d) decode JSON string escapes (`\"`, `\\`, `\/`, `\uXXXX`) before comparison, or reject any value containing an escape sequence the decoder does not implement — never compare raw bytes containing escapes; (e) require `type == "webauthn.get"`, `origin ==` the account's stored expected origin, `challenge == base64url(transcript hash)`; (f) if a top-level `crossOrigin` key is present it must be `false`; (g) unknown top-level keys are ignored but still counted for the duplicate check. **Replay:** the transcript preimage is **canonical and byte-exact** — `transcript_hash = Keccak256("WARDEN/root/v1" ‖ cluster_tag[32] ‖ program_id[32] ‖ account[32] ‖ generation:u64 LE ‖ policy_version:u32 LE ‖ root_nonce:u64 LE ‖ expiry_ts:i64 LE ‖ **signed_slot:u64 LE** ‖ action_hash[32])`, and the WebAuthn challenge is `base64url(transcript_hash)`. **`signed_slot` sits between `expiry_ts` and `action_hash`** — the position is part of the ABI, not an implementation detail, and Rust, the `packages/core` mirror and the IDL must agree on it byte-for-byte or every ceremony either forges or bricks (this is prior-art finding `LZR-ACC-H2`: write/read layout drift). A golden vector pins it., where **`cluster_tag` is a client-attested 32-byte domain separator stored in `SmartAccount` at creation — NOT a verified genesis binding** (rev 6 said `genesis_hash`, which overstated it: a Solana program cannot read the cluster's genesis hash, so the value is whatever the extension wrote at `create_account`, by convention `getGenesisHash()`). It guarantees that an assertion produced against one stored tag cannot be replayed against an account holding a different tag; it does **not** guarantee the tag names the cluster the transaction lands on. It is non-zero-checked at creation (`ZeroClusterTag`, 6026) and immutable in Phase 1A.

**Root nonce = an odometer, not a set (wording corrected in rev 8).** `SmartAccount.root_nonce` is a **consumed scalar nonce with strict `n+1` equality**: the transcript carries the account's current `root_nonce`, the program requires exact equality with the stored value, and increments it atomically by one on every successful root instruction. Storage is **O(1)** — a single `u64` — and there is no "consumed-nonce set", no replay bitmap and no rent that grows with usage. Earlier revisions said "consumed nonce"/"consumed-nonce set", which invites a future engineer to "fix" a rent-growth problem that does not exist. Do not replace this with a set-based or window-based scheme: strict `n+1` is what makes a captured assertion unusable the instant any other root instruction lands, and it is stronger than the schemes LazorKit and Swig ship.

**Freshness is slot-based (rev 8).** The transcript's `expiry_ts` alone is not the freshness control. `Clock::unix_timestamp` is a **stake-weighted estimate** that can drift from wall clock by minutes; `slot` is the consensus-native clock every peer anchors to. So the transcript additionally carries a client-signed `signed_slot: u64` (position fixed by the canonical preimage above), and the program requires:

**`signed_slot ≤ Clock::slot < signed_slot + MAX_ROOT_SLOT_AGE`**, with **`MAX_ROOT_SLOT_AGE = 150`** — written as one chained inequality because both halves are load-bearing and the boundary is exclusive on the upper side:

- the left half rejects a **future slot outright** (a client cannot buy itself a longer window by signing ahead; without it the window is one-sided), and
- the right half is a **strict** bound: an age of exactly 150 slots is **rejected**, 149 is accepted. `MAX_ROOT_SLOT_AGE = 150 slots (≈60 s)` on the default root path — the same order as LazorKit (150) and Swig (60), and 10–25× tighter than the 600 s wall-clock window rev 7 relied on.

`expiry_ts` stays, with `now ≤ expiry_ts ≤ now + 10 min`, but it is now the **secondary** bound and its long tail exists only for Phase 1C's deferred/timelocked flow (`queue` → `execute_pending`), where an action is deliberately signed well before it executes and the slot window cannot apply. On the default path both checks must pass. This is not a free change: it adds a field to `RootArgs`, to `root_verify/transcript.rs`, to the `packages/core` transcript mirror and to the IDL, it requires the client to fetch a slot before the ceremony, and it consumes part of the measured root-ceremony byte budget (680 B used, ≈552 B of payload headroom at 1A) — Phase 1B re-measures.

**Change set (complete, because a partial one silently forges or bricks ceremonies).** `signed_slot` is added to `RootArgs`, to the canonical preimage in `root_verify/transcript.rs`, to the `packages/core` TS mirror (`packages/core/src/webauthn/transcript.ts`), and to the IDL — and to **every one of the six Phase-1A root callers**: `rotate_nonce`, `grant_session`, `revoke_session` (root path), `transfer` (root path), `freeze`, `unfreeze`. Phase 1B's new root paths (`create_account` with proof-of-possession, `execute`, `swap`) carry it from the start. A **golden vector** generated in TS and re-hashed in a Rust test pins the byte layout across the language boundary. **`action_hash` = Keccak256 of the canonical action encoding**: `op_type(u8) ‖ borsh(op_args)` where `op_args` includes, for every instruction the root authorizes, the *complete* semantic inputs — for `transfer`: mint, to, amount; for `execute`/`swap`: the exact compiled instruction list (program id, ordered account metas incl. is_signer/is_writable, data) or the Stage hash; for `queue`/`set_policy`/`grant`/`contest`/`unfreeze`/`set_guardians`: the full borsh-serialized argument struct. The program recomputes the hash from the instruction it is executing and rejects on mismatch, so no argument or account can be swapped after the passkey ceremony. A blockhash is deliberately **not** part of the transcript (a program cannot authenticate the outer message's blockhash). Sign counter advisory only (synced passkeys). The private key never leaves the authenticator; the extension cannot export it. Ed25519 root kind exists for hardware/advanced users and is not the default.

**Session key.** Ed25519 keypair in the service-worker keyring (AES-256-GCM; unlock secret from passkey PRF **where available**, fallback Argon2id password — PRF is confirmed only on a CDP *virtual* authenticator (spike §12.2); real-device PRF is UNVERIFIED, so **the Argon2id fallback is mandatory in v1** and PRF is an optimisation, never a requirement), unlocked for a window (default 15 min idle / 8 h max). Signs routine actions within caps. Multiple sessions (devices, agents) share **account-wide** daily caps; each also has a lifetime cap.

**Guardians.** Up to 5 typed pubkeys (Ed25519 or P-256 passkey of a second device) with threshold (default 2-of-3): second device, a friend's wallet, and the optional **drinkerlabs cloud guardian** (a service key that can only `approve_recovery` and `freeze`, after email magic-link + TOTP + 24 h cooling). Guardians can freeze (bounded, §5.1) and approve recovery; nothing else.

**Recovery key.** At onboarding the extension generates an Ed25519 *recovery key*, registers it on-chain as a guardian with weight = threshold, encrypts it into a versioned envelope (Argon2id id=2, m=256 MiB, t=3, p=1; AAD = account address ‖ version) under a **128-bit recovery code** (12 BIP-39 words) shown once and exportable to file/QR. It can *only* propose+approve recovery — it cannot move funds and is subject to the same delay and root contest. It **is** a bearer secret with threshold weight (materially seed-like, but delayed, contestable, and freeze-able); users who prefer no such secret can decline it and rely on guardians alone. Losing it loses nothing while guardians remain.

**What a session cap bounds, exactly (v1 / Phase 1A, implemented):** a session's OWN caps are **`per_tx` and `lifetime_cap`, and nothing else** — i.e. the bound one session gives you is `per_tx × (number of calls) ≤ lifetime_cap`. The **day and rolling-30-day windows are ACCOUNT-WIDE**: they live in `SmartAccount.buckets` and every session *and* the root debit the same ones, so ten sessions do not get ten day caps. Phase 1A therefore **rejects** a `grant_session` that sets a non-zero per-session `per_day`/`per_30d` (`SessionDayCapsUnsupported`, 6033) rather than storing a cap nothing enforces. Per-session day buckets are deferred to **Phase 1C**, where they ride on the single `DayBuckets` PDA specified in §5.2 rule 4 (a 30-slot ring is 264 B and does not fit `SessionKey`'s 64 B reserve); `policy.session_ceiling`'s `per_day`/`per_30d` comparisons stay in the code, unreachable, until then, and **1B keeps rejecting per-session day caps at grant**.

**An expired or revoked session's caps are EXHAUSTED, not ABSENT.** A session past `expiry_ts`, or whose `generation_at_grant` is stale, or that has been revoked, is treated as *having zero remaining allowance* on every axis — not as an account with "no cap configured" and certainly not as an unbounded one. Every cap comparison must be written so that the failure mode of a missing/expired session record is `outflow == 0` (reject), never "no cap found ⇒ skip the check". This is the shape of LazorKit ACC-C2 (an authorisation branch that skipped a check instead of failing it) and it is the difference between a fail-closed and a fail-open wallet. The same rule governs a mint with no cap entry: **no cap ⇒ outflow must be exactly 0**, never "unlimited" (already stated in §5.2 rule 4; restated here because it is the same invariant).

**Default policy (user-editable; loosening is timelocked):**
- Session caps (account-wide/day; per-tx): SOL 0.5 / 2; USDC & USDT 100 / 500. Other mints: no transfer/execute outflow unless a cap is set. Read the day figure as the account-wide bucket per the paragraph above, not as a per-session allowance.
- Swap caps (input side, per mint per day, account-wide): SOL 5, stables 2,000, other mints 100% of holdings *only if* out_mint ∈ `allowed_out_mints` (default: SOL, USDC, USDT). Swaps into other mints require an explicit cap or the root.
- Large threshold = anything above session caps → root ceremony **and** timelock (default 12 h, min 1 h). Recipient allowlist entries (added via timelocked loosening) skip the delay for that recipient only.
- Account-wide **rolling 30-day cap** per mint across all sessions *and* root direct actions (default SOL 20, stables 5,000) — the bound a patient attacker with the root passkey ceremony faces.
- Recovery delay 48 h; guardian-freeze max 72 h (indefinite while a recovery proposal is open, §5.1).

## 5. On-chain program

### 5.1 Instructions

| Instruction | Signer | Effect / invariants |
|---|---|---|
| `create_account(root_key, root_assertion, salt, rp_id_hash, origin, cluster_tag, policy)` | payer + **root passkey ceremony** | **The address is root-bound and creation is authenticated (Phase 1B Task 2b — this closes the 1A squatting hole).** The PDA seed is computed ON-CHAIN as `owner_seed = Keccak256("WARDEN/seed/v1" ‖ root_pubkey33 ‖ salt32)` and the account lives at `["account", owner_seed]`; `salt` is 32 client-chosen random bytes and **`owner_seed` is no longer an argument**. The address is therefore a hash of (root, salt): not derivable from the root alone without the salt, and **not squattable** — a front-runner who copies the salt but substitutes their own root derives a *different* address, and reaching the victim's address requires the victim's root key, for which the instruction ALSO demands a real assertion over `action_hash(0x06, borsh(CreateBody{ salt, rp_id_hash, origin, cluster_tag, policy_hash = Keccak256(borsh(PolicyArgs)) }))`. The transcript uses `generation = 0`, `policy_version = 1`, `root_nonce = 0`, the derived address, `cluster_tag` from the args and `signed_slot`; on success the account is written with **`root_nonce = 1`** (the creating ceremony is consumed). Like every root path it is **top-level only** (`RootRequiresTopLevel`). **Phase 1B measured limits:** at most **`MAX_MINTS_AT_CREATE` = 1 mint** may be configured in one instruction — the ceremony costs **+477 B** (182 B precompile instruction, 226 B `RootArgs`, the Instructions sysvar account), so 0 mints = 949 B, 1 mint = 1,117 B and **2 mints = 1,285 B does not fit** the 1,232 B packet (1A allowed 4 at 1,144 B). Mints 2–8 are added later by `set_policy` (1C). `rp_id_hash` is recomputed on-chain as SHA-256(origin) and the `origin` must be exactly `chrome-extension://` + a 32-char `a..p` extension id; `cluster_tag` must be non-zero; the root must be a P-256 compressed-point encoding (Ed25519 roots are refused). **The off-curve-x gap is closed as a side effect**: the secp256r1 precompile cannot verify a signature under a point it cannot decompress, so an off-curve root cannot be created at all. The extension should still read the account back and verify `root == its passkey` before showing a receive address — but that is a client-correctness check now, not a mitigation for a live attack. |
| `grant_session(...)` | root | Caps ≤ `policy.session_ceiling` per mint, `ops_mask ⊆ policy.session_ops_ceiling` **and ⊆ the bits this program has assigned** (unknown bits are refused — an unassigned bit would silently become authority the day a later version assigns it), expiry ≤ `policy.max_session_life`. **Phase 1A: at most `MAX_CAPS_PER_GRANT` = 2 caps per grant** (measured: a 2-cap grant is 976 B of the 1,232 B packet, and `clientDataJSON` may legally grow to 512 B), and **`program_allowlist_id` must be 0** until the Phase 1B adapter registry exists (`ProgramAllowlistUnsupported`) — a non-zero id would persist a dangling reference. A grant into an existing session **merges by mint** and refreshes `generation_at_grant`, so the signed body carries `prior_authority_hash` — the hash of the retained authority (identity + every cap slot + lifetime caps) the merge is allowed to merge into — and a mismatch is refused (`SessionPriorStateMismatch`): the ceremony binds the authority it produces, not only the fields it names. Grants above ceiling → must go through `queue(Grant)` |
| `revoke_session(pubkey)` | root or that session | Closes |
| `transfer(mint?, to, amount)` | session (within caps) or root (≤ `large_threshold` per tx **and debits the same account-wide day/30-day buckets** — root direct spend is bounded like a session; larger → queue) | Native or SPL; day-bucket + lifetime accounting; `to` must not be a vault-owned token account; ATA creation for `to` funded by the outer fee payer, never the vault |
| `swap(route)` | session or root | Jupiter CPI, §5.2 |
| `execute(stage?, ixs?)` | session or root | Allow-listed dApp CPI with conservation checks, §5.2. Root execute above threshold must be queued |
| `stage_open(hash, len)` / `stage_chunk(off, bytes)` / `stage_finalize` / `stage_close` | any payer | Chunked upload; finalize checks Keccak256(content) == hash and records `generation` + `policy_version`; consume-once (closed on use); expiry ts; anyone may close after expiry. **`stage_chunk` account layout (fixed here so the payload cap becomes deterministically measurable instead of resting on an assumed shape): exactly three accounts in this order — (0) payer, signer + writable; (1) Stage PDA `["stage", account, hash]`, writable, not a signer; (2) System program, read-only. Instruction data = the program's 8-byte discriminator ‖ header `offset: u32 LE ‖ len: u32 LE` ‖ exactly `len` payload bytes.** The spike measured **985 B of payload** for a transaction of this account shape but with **no discriminator** in the data (spike §12.3), so the cap for the encoding above is at most ≈977 B. **Both numbers are PROVISIONAL** — `stage_chunk_payload_cap` is measured against the built program in Phase 1 and recorded here; nothing may depend on a hard-coded 985. Chunk count for a staged payload = `ceil(len / stage_chunk_payload_cap)` |
| `queue(action)` → Pending | root | Content-hashed action (transfer/execute/policy/grant); `execute_after = now + timelock` |
| `cancel_pending(nonce)` | root or any guardian | Closes |
| `execute_pending(nonce)` | permissionless after `execute_after` | Re-validates against **current** policy and generation; refuses if frozen |
| `set_policy(policy)` | root | Tightening applies immediately; any loosening (§5.5) rejected here → must be queued |
| `freeze` | root or guardian | Root freeze: indefinite until root `unfreeze` (after timelock). Guardian freeze: `until = now + guardian_freeze_max`, one active at a time, per-guardian cooldown 7 d; **once a Recovery proposal has reached guardian threshold (approvals ≥ threshold), the guardian freeze does not expire while that proposal is open** — a single guardian cannot freeze indefinitely |
| `unfreeze` | root | Root freeze: after timelock. **The timelock is read LIVE from `policy.timelock_secs` at lift time, not snapshotted at `freeze` time** (Phase 1A behaviour, no 1A instruction can change it) — **1B's `set_policy` must therefore make a deliberate choice for an account that is already frozen: preserve the live read (a shortened timelock also shortens an in-progress freeze) or snapshot the value at `freeze` time.** Guardian freeze: **only via a queued (timelocked) action, and never while a threshold-approved Recovery proposal is open** — the root cannot insta-lift a guardian freeze |
| `propose_recovery(new_root, nonce)` | guardian | Immutable proposal; approvals bound to content hash |
| `approve_recovery(nonce)` | guardian | At threshold: `ready_ts = now + recovery_delay` |
| `execute_recovery(nonce)` | permissionless after `ready_ts` | Refused while the proposal is *contested* (below); replaces root, `generation += 1` (invalidates every session, stage, pending) |
| `contest_recovery(nonce)` | root | Root ceremony that pushes `ready_ts += recovery_delay`; unlimited, each is a liveness proof. There is no root `cancel`. Guardians may withdraw a proposal (threshold) |
| `set_guardians` | root via queue (2× timelock) | **Guardians may cancel this pending action** (threshold) — symmetric with root's contest |

**Root-vs-guardians conflict (stated outcome):** the design is deliberately symmetric — root can contest recovery indefinitely, guardians can freeze indefinitely while a proposal is open and can cancel guardian-set changes; root direct spend is bounded by the account-wide buckets and blocked entirely under a guardian freeze. So an attacker who holds the root passkey but not the guardians is bounded by the account-wide day bucket per day / 30-day cap per month across *all* root paths (§5.2.4), and by any guardian freeze; a threshold of guardians can freeze indefinitely and recover; a single rogue guardian can only freeze for `guardian_freeze_max` per cooldown; a legitimate user facing colluding guardians (≥ threshold) ends in **funds frozen, not stolen** — the exit is the off-chain human process of the drinkerlabs cloud guardian (identity-verified) siding with the identified owner, or the guardians relenting. This is the honest bound; it is documented in the product.

Cross-cutting: `frozen` gates every outflow and session use; every PDA re-derived from seeds; **checked arithmetic everywhere** (overflow = abort); every account `version: u8`; **self-CPI into the warden program is rejected**; **every root instruction additionally requires `get_stack_height() == TRANSACTION_LEVEL_STACK_HEIGHT`** — a root path may only be invoked as a **top-level** instruction, never through a middleman program (adopted from LazorKit, MIT; `grep -rn stack_height programs/warden/src/` returns nothing today, so this is a 1B change). Rejecting CPI callers on the root path removes a whole class of "what could an intermediate program do to the Instructions-sysvar view" reasoning, and it is distinct from the existing "self-CPI into warden is rejected" rule, which only blocks warden→warden. Bucket/day arithmetic uses `Clock.unix_timestamp`; **root-ceremony freshness uses `Clock.slot`** (§4) — the two clocks serve different jobs and neither replaces the other. Day buckets are fixed UTC days — the honest bound across a boundary is 2× the daily cap and the UI says so; lifetime caps and per-tx caps are exact.

### 5.2 Conservation checks for `execute` and `swap` (the load-bearing part)

`execute` runs the CPIs itself, so it can snapshot before and after in one instruction.

**`execute` payload contract (measured, spike §12.3) — indices are LOGICAL, and this mapping is canonical everywhere (spec, program, SDK, tests).** The payload encodes each inner instruction's accounts as indices into the **logical account list**, defined exactly once as:

```
logical[0]   = smart_account            (the SmartAccount PDA)
logical[1]   = signer                   (the session key, or the payer on the root path)
logical[2+k] = remaining_accounts[k]    (the dApp accounts, in client order)
```

**The handler BUILDS this logical list from its own named accounts plus `remaining_accounts`; it does not assume the physical order matches.** The Anchor context carries named accounts (`smart_account`, `signer`, `session: Option`, `ix_sysvar: Option`, `stage: Option`, `registry: Option`, and in 1C `day_buckets: Option`) *before* `remaining_accounts`, so the **physical** slice is `[smart_account, signer, session?, ix_sysvar?, stage?, registry?, remaining…]` and the physical position of `remaining_accounts[0]` varies with which optionals are present. Logical indices are immune to that by construction; **no index in the payload ever refers to a physical slot, and no code may index the raw account slice directly.** This is also not an index into the compiled message's global account-key table — on-chain the handler only ever sees its own instruction's account slice.

`accounts_hash` (bound by `ExecuteBody`/`SwapBody` on the root path) is computed over the **logical list, in logical order** — `for each logical account: pubkey ‖ is_signer ‖ is_writable` — so the root assertion binds the same object the payload indexes. The SDK MUST, after compiling, decompile the transaction, **reconstruct the logical list the same way the handler will**, and assert it equals the order it encoded against, and that no key appears twice in that list (a duplicate shifts every later index). The **snapshot scope is every `remaining_account`, writable or not** (read-only accounts can still be vault-owned; the extra cost is cheap insurance), **plus the SmartAccount PDA's own lamports**, tracked separately for the SOL equation. **Compute-budget instructions are top-level only** — `ComputeBudgetProgram` instructions are honored by the runtime solely at the transaction's top level and are silently inert inside a CPI, so the wrapper hoists any the dApp supplied into the outer instruction list (never into the payload) and adds a default `setComputeUnitLimit(600_000)` when the dApp tx carries none (~40 B). **Account cap (PROVISIONAL):** a session `execute` accepts at most **40 accounts**, pending Phase 1 re-derivation with the corrected metric below. This is a **byte-driven** bound, not a CU-driven one: a real 43-account Jupiter route already serialized to 1,235 B against the 1,232-B packet limit while a 35-account route fit, so 40 sits just below the observed breakpoint. **That 35–43 band is a `totalKeys` measurement — every key in the original, pre-wrap message (static + LUT, signer or not, writable or not) — not a writable-account-only count:** the spike's measurement script mislabeled this metric as `writableAccounts` while actually computing the total-key count; it has since been corrected to report `totalKeys`, `writableKeys` (payer + writable statics + writable LUT indexes), and `executeAccountCount` (the wrapped `execute` instruction's own account-list length) separately, but only `totalKeys` was captured for the runs that produced the 35–43 band — `writableKeys` and `executeAccountCount` are unmeasured. **The 40 cap therefore stays PROVISIONAL and must be re-derived in Phase 1** once routes are re-measured with the corrected metrics (spike §12.3, result.md "Round 5 fix"). The conservation snapshot's own cost is measured at **≈900 CU per account** over a ≈1,400 CU base (spike §12.3), i.e. ≈37k CU at 40 accounts — but that measurement **isolates the snapshot and contains no CPI**, so it says nothing about a whole `execute`. **Phase 1 must measure a complete `execute` (snapshot + real inner CPI + compute-budget instruction) end to end and lower this cap if combined CU, rather than bytes, binds first.** Root `execute` is subject to the same cap.

Rules:
1. **Adapter registry, not a bare allowlist.** Session `execute` may CPI only to `(program_id, instruction discriminator)` pairs in the session's registry (policy-defined; default = a curated set — SPL Token/ATA/System/Memo plus typed entries for Jupiter and a handful of major protocols shipped with pinned discriminators and per-adapter account-role rules), extendable only via timelocked loosening. Program-id pinning does not pin upgradeable code — stated limitation; the registry is reviewed and shipped as data. **Discriminator provenance (spike §12.4):** the compat inventory produced a 15-entry `(program_id, discriminator)` seed list, but only two entries are ground truth (Meteora DLMM `swap`, IDL-embedded; Pump.fun `buy`, published) — **the rest, including Jupiter v6 `route`/`sharedAccountsRoute` which §5.2.7 pins, are UNVERIFIED and MUST be re-derived programmatically from each program's IDL before shipping**. Anchor sighashes hash the instruction *name* only, so identical names collide across programs (Marinade `deposit` and Drift `deposit` are byte-identical) — the registry key is therefore always the `(program_id, discriminator)` **pair**, never a discriminator alone. Non-Anchor programs (Raydium AMM V4, Phoenix, SPL Stake Pool, spl-governance, Solend/Save) have no sighash at all and need per-program tag/layout rules in the adapter entry. **Selector derivation rule (binding):** an adapter entry's selector is derived from the program's **IDL sighash** where an Anchor IDL exists, and from the **per-program instruction tag** where one does not — SPL Token, SPL Token-2022, System, Memo and the Associated Token program all use a single-byte (or fixed-layout) tag, **not** an 8-byte discriminator, so `disc_len` is part of the entry and a selector must never be assumed to be 8 bytes. Root `execute` may target any program (conservation-checked; above threshold, queued).

   **1a. Fixed deny-list, above and outside the registry — the floor policy cannot reach.** A set of `(program, instruction)` pairs is **hard-coded in the `execute` payload decoder**, evaluated on **every inner instruction on BOTH the session path and the root path**, *before* dispatch and *before* any registry lookup. It is not a registry entry, not policy data, and **not reachable by §5.4's loosening lattice** — §5.4 says loosening *extends* the registry, so a deny that lived only in the registry would not be a floor at all, and the root path skips the registry entirely, so a deny enforced at `registry_allows` would not cover the root path in any form. The deny-list is:

   | Program | Instruction | Rule |
   |---|---|---|
   | SPL Token **and** Token-2022 | `SetAuthority` (tag `6`) | **Reject unconditionally.** Authority transfer on a token account or mint is the most damaging Solana-specific drainer pattern and is irreversible even for the rightful key holder |
   | SPL Token **and** Token-2022 | `Approve` (tag `4`) | **Reject unconditionally.** A delegate is a standing withdrawal right that outlives the transaction and every cap |
   | SPL Token **and** Token-2022 | `ApproveChecked` (tag `13`) | **Reject unconditionally**, same reason |
   | SPL Token **and** Token-2022 | `Revoke` (tag `5`) | **Reject unconditionally.** Not a theft primitive, but it mutates `delegate`/`delegated_amount` on a vault account, which §5.2 rule 2 requires to be byte-identical before/after; denying it in the decoder turns a confusing late conservation failure into a precise early one |
   | SPL Token **and** Token-2022 | `CloseAccount` (tag `9`) | **Reject, with exactly ONE exception — the *vault-sweep* case, defined below.** Closing a vault ATA to a stranger is a rent-drain of exactly the shape audited on `revoke_session` |

   **Discriminator values are UNVERIFIED against SPL source and MUST be verified before implementation** (research §4 item 12): the implementer re-derives each tag from `spl-token`'s `TokenInstruction` enum at the pinned crate version, records the crate version and the source path in `docs/program/PHASE1B-MEASUREMENTS.md`, and a unit test asserts each constant equals the value the crate encodes. A wrong tag here is a silent hole, not a compile error. **A registry entry may not re-enable a denied pair** — the decoder runs first and there is no override flag; a test asserts a registry list containing `SetAuthority` still fails closed.

   **The vault-sweep exception — the ONLY way a vault-owned token account may legally disappear (rev 8, and it is deliberately narrow).** A vault-owned token account may be closed **if and only if all four conditions hold**:

   1. the close is a **direct SPL Token / Token-2022 `CloseAccount` inner instruction of the `execute` payload** — i.e. the payload decoder can see its `(program_id, tag)` and read its account list itself;
   2. the account's `amount` in the **BEFORE** snapshot is **exactly 0** (nothing of value is being swept — only rent);
   3. the instruction's **rent-destination account decodes to the SmartAccount PDA** (SPL `CloseAccount` account order: `[0] account, [1] destination, [2] authority`), so the lamports come home; and
   4. the account is not the SmartAccount PDA itself and is not a Mint.

   **A close that reaches the token program nested inside some other program's CPI is NOT exempt**, whatever its destination. The payload decoder sees only the instructions the payload names; it cannot see what an allow-listed program does one level down, so it cannot establish conditions (2) or (3) for a nested close. Nested closes therefore fall through to §5.2 rules 2 and 3 and are **rejected there** as "a vault-owned token account that existed BEFORE does not exist AFTER". This is deliberate asymmetry: the decoder is a *whitelist of closes it can prove*, not a *blacklist of closes it dislikes*.

   The decoder emits, for each permitted close, a **decoded close intent** `{account, destination, amount_before}` that is handed to the conservation comparison (§5.2 rules 2/3) and to value accounting (§5.2 rule 4a). Nothing downstream may infer a close from a disappearance — it must be told, or it rejects.
2. **Snapshot every remaining account (writable or not) plus the SmartAccount PDA's lamports and every required Mint** in the instruction: existence, owner program, lamports, data length, and for token accounts (SPL + Token-2022) `(mint, owner, amount, delegate, delegated_amount, close_authority, state, is_native)` plus, for Token-2022, a hash over the full extension TLV bytes. **The comparison is before/after, field by field** — it is not enough to inspect the after-state, because a *pre-existing* delegate or close-authority that the CPI **clears** would otherwise pass, and an account that becomes unparseable would otherwise be silently skipped. Concretely: for every account whose BEFORE snapshot is a vault-owned token account, the AFTER snapshot must still parse as a token account **unless the payload decoder handed the comparison a matching decoded close intent for that exact account (rule 1a's vault-sweep exception)** — absent such an intent, a vault-owned token account that existed BEFORE and does not exist (or does not parse) AFTER is a **reject**, which is precisely what catches a close nested inside another program's CPI. Where the account survives, **every field except `amount` must be byte-identical before vs after** — runtime owner, token owner, mint, delegate value, `delegated_amount`, `close_authority` value, `state`, `is_native`, `data_len`, TLV-tail hash — *and*, independently of whether anything changed, the after-state must satisfy policy (`state == Initialized`, `delegate == None`, `close_authority == None`). COption tags are decoded **strictly** (`0` = None, `1` = Some, anything else = parse error), never as `tag != 0`. Measured cost (spike §12.3): **10,011 / 18,785 / 27,225 CU for 10 / 20 / 30 vault-owned SPL token accounts** ⇒ ≈1,400 CU base + **≈900 CU per account**; a Token-2022 account with a 100-B TLV tail adds ≈1,140 CU, and keccak vs SHA-256 for the TLV hash is CU-identical at that size (keccak is the default). **These figures isolate the snapshot: the spike harness performs no CPI between the two passes, and `is_native` was not among the fields it compared.** A real `execute` adds the inner CPI's CU on top, and the reject-on-mutation branch has only been proven by direct unit tests on the comparison function, never end to end through a CPI. Phase 1 measures the complete instruction and exercises a real mutating CPI against it. On the snapshot alone, ~900 CU/account is not the binding constraint — the 1,232-B packet limit is (see the account cap above).

   **2a. Mint accounts are in the snapshot set (rev 8).** Snapshotting only token accounts leaves the *mint* — where `mint_authority`, `freeze_authority` and, on Token-2022, the fee authorities live — entirely unobserved. A CPI that hands itself the mint authority of a mint the vault controls passes every rule-2 check today. So:

   - **Presence rule (tightened, Phase 1B Task 1 round-1 review).** Whenever a **vault-owned token account of mint M is present** in the instruction — *writable or not* — **M's mint account MUST be present in the transaction**, else reject. The rule was originally written as writable-only; that let a caller opt out of the danger-extension check (rule 5) and the authority comparison below simply by passing the vault ATA read-only, so the gate was removed. Cost is one extra account in the list for a case that is rare in practice. This costs nothing new: rule 5's Token-2022 danger-extension check already requires the mint account to be present for any T22 vault token account touched, so this generalises an existing requirement to classic SPL mints.
   - **Snapshot rule (tightened, Phase 1B Task 1 round-1 review).** If the vault holds **any** authority on M — `mint_authority`, `freeze_authority`, or (T22) `transfer_fee_config_authority` / `withdraw_withheld_authority` — then M is snapshotted before and after, and **every authority field is compared byte-for-byte, plus `decimals` and the TLV-tail hash**. This comparison is **independent of whether any vault token account of M is in the instruction at all**: the vault can be a mint's `mint_authority` while holding none of its supply, and handing that authority away is exactly the irreversible loss rule 1a's `SetAuthority` row exists to prevent. It also runs **before** the rule-1a close branch, so closing a zero-balance vault ATA in the same instruction cannot skip it. If the vault holds no authority on M, the mint is read (for the extension check) but not authority-compared.
   - **Parsing, stated rather than implied.** A **classic SPL mint is a fixed 82-byte layout**: `mint_authority: COption<Pubkey>` (36 B), `supply: u64`, `decimals: u8`, `is_initialized: bool`, `freeze_authority: COption<Pubkey>` (36 B). COption tags decode **strictly** (`0` = None, `1` = Some, anything else = parse error), exactly as for token accounts. A **Token-2022 mint is the same 82-byte base plus a TLV tail**; the extension authorities live *inside* that tail, so `TransferFeeConfig`'s `transfer_fee_config_authority` and `withdraw_withheld_authority` are **extracted explicitly by TLV type and offset** and compared as fields. **A whole-tail hash is NOT sufficient here** and must not be used as the mint's authority control: a legitimate `transfer_fee` accrual (`withheld_amount`) mutates the same tail and would trip a tail-hash comparison on the happy path, so a tail hash produces false positives while the field extraction produces the true answer. (The whole-tail hash stays as the control for *token accounts* per rule 2, where no legitimate CPI mutates the tail.)
   - **Verdict rule.** A change to any snapshotted mint authority field is an **instruction reject** (`ConservationViolated`), **not** an accounting entry. There is no amount that makes handing away a mint authority acceptable, so it never enters the outflow equation.
   - `supply` is *not* an authority field: a legitimate mint/burn through an allow-listed adapter changes it. It is snapshotted and recorded for the intent view, and is not by itself a reject.
3. **Vault-owned accounts** (owner == SmartAccount PDA, or token accounts whose authority is the PDA): after CPIs, `owner` unchanged, `delegate == None`, `close_authority == None`, `state == Initialized`, **not closed — with the single vault-sweep exception of rule 1a (direct decoded `CloseAccount`, `amount_before == 0`, destination = the SmartAccount PDA); every other disappearance, including any close nested inside another program's CPI, is a reject** — not realloc'd. The SmartAccount PDA itself may not be writable to any CPI target. **No other vault-owned account types are allowed to be writable** (stake accounts, nonce accounts, program-owned state with the vault as owner) — unsupported in v1, rejected. Three additions from the Phase 1B Task 1 round-1 review, each closing a fail-open path:

   - **An account may not BECOME the vault's.** If an account parses AFTER as a token account whose authority is the PDA, it must have been the *same* vault-owned token account, of the same mint, under the same program, BEFORE — otherwise reject. Classification driven only by the BEFORE snapshot silently ignored an account a CPI created (or converted) mid-instruction, including one carrying an attacker delegate. Account creation is funded by the outer fee payer at transaction level (rule 4), so this rejects nothing a well-formed client does.
   - **Lamports on a NON-native vault token account must not move.** Token-2022's `WithdrawExcessLamports` moves an account's lamport balance while leaving every field rule 2 compares byte-identical. Native (wrapped-SOL) accounts are exempt because their lamports back `amount`, which the rule-4 SOL equation already counts — `is_native`, not the mint key, is the field that decides.
   - **Duplicate account keys are rejected.** The before/after arrays are compared positionally, so one account listed at two indices is read twice and its net change is under-counted (a vault ATA listed twice while 100 tokens leave nets to 50). The SDK already asserts the logical list is duplicate-free; a duplicate reaching the program is a malformed payload.
4. **Value accounting.** For each SPL mint, `outflow[mint] = Σ(amount_before − amount_after)` over vault-owned token accounts of that mint (negative ⇒ inflow, floored at 0 for cap purposes). **SOL:** `outflow[SOL] = (pda_lamports_before − pda_lamports_after) + Σ_{vault WSOL accounts}(amount_before − amount_after)`; WSOL token-account *lamports* are not counted separately (they back the `amount`), so no double count. **No rent exemption**: account creation is always funded by the outer fee payer, never the vault. Session: `outflow[mint] ≤ per_tx[mint]` and day/lifetime buckets updated with checked math; a mint without a cap ⇒ outflow must be 0. **Root (every direct path — `transfer`, `execute`, `swap`): `outflow[mint] ≤ large_threshold[mint]` per tx *and* debits the same account-wide day and rolling-30-day buckets;** anything beyond must come from `execute_pending`, whose execution *also* debits the buckets (a queued action is delayed and visible, not exempt from the 30-day bound). The one-line consequence: a root attacker without guardians extracts at most the account-wide day bucket per day and the 30-day cap per month, before any freeze.

   **4a. `CloseAccount` rent lamports, and how accounting learns about them.** For a **WSOL** account the lamports back the `amount` and are already counted once by the equation above — no change. For a **non-WSOL** vault token account, the rent-exempt lamports returned by `CloseAccount` are invisible to *both* halves of the equation: they are not the PDA's lamports, and (under rule 1a's exception) the token `amount` was zero. **Accounting is therefore never allowed to infer a close from a disappearance.** It receives the payload decoder's **decoded close intents** `{account, destination, amount_before}` (rule 1a) as an explicit input, and:

   - **Permitted vault-sweep close** (destination = the SmartAccount PDA): the returned rent lamports arrive as an **increase in the PDA's own lamports**, which the SOL equation already sees as an inflow. Nothing extra is added — adding it again would double-count. The intent's role here is to tell rule 2/3 the disappearance was legal.
   - **Any close whose decoded destination is not the vault PDA**: the instruction is **rejected by the decoder before the CPI runs**. If such a close is nonetheless reached in a unit-level test with the decoder stubbed out, its `lamports_before` of the closed account are added to `outflow[SOL]` — this is the backstop, and it must be tested independently of the floor so that neither control is passing only because the other fired first.
   - **A close the decoder never saw** (nested inside another program's CPI): accounting is not involved at all — §5.2 rules 2/3 reject the transaction on the unexplained disappearance.

   The two controls are deliberately redundant: the deny-list is the floor, the accounting entry is the backstop, and neither is allowed to be the only one.

   **4b. The intra-CPI blind spot, and the bound 1B actually enforces.** Rev 7 implied that finer-grained snapshots could close every accounting gap. They cannot, and rev 8 says so plainly: **a before/after snapshot — at any granularity, including per-inner-CPI — cannot observe a round trip that happens inside a single CPI.** If one DEX instruction moves 100 SOL out of the vault and 99.5 SOL back within its own execution, the net diff the program sees is 0.5 SOL, and no snapshot design (ours or any peer's) sees the 100. This is a **semantic boundary of the whole approach**, restated in §5.3, not a gap to be engineered away. Note also that there is **no prior-art precedent for token gross-turnover accounting**: LazorKit's gross accounting is *SOL summed between outer CPIs*, and its token per-transaction limit is an ordinary before/after net diff. **1B therefore introduces no `gross_turnover` field and no gross bucket.** What 1B enforces instead, per transaction:
   - the **adapter-decoded source limit** — the `max_in` the adapter *parses out of the inner instruction's own data* (not inferred from balances), compared against the session's `per_tx` and the account buckets before the CPI runs; and
   - a **pinned source token account** — the adapter's role validator requires the inner instruction's source account to be the specific vault ATA the caller declared, so the value at risk in the call is bounded by an account the program named rather than by whatever the route touches.

   Together these bound a session's exposure *per call* by a number the program **read**, which is the strongest available control given the blind spot. Whether it is sufficient in practice is an explicit **design bet**, recorded as such (research §4 item 15), not a proven property.

   **4c. Persistent gross-day accounting, if adopted at all, is Phase 1C and rides on ONE new account.** It shares the `DayBuckets` PDA that per-session day buckets need — they are two columns of the same table, which is why they cannot be scheduled apart, and why 1B defers both together rather than shipping either alone. Specified once, here, and identically in the 1C plan:
   - **Seeds:** `["daybuckets", account]` — exactly one per `SmartAccount`.
   - **Contents:** a fixed-capacity table of `(session_pubkey, day_ring[30], gross_ring[30])` rows plus a free-slot bitmap. The per-session day arrays and the gross arrays are columns of the same rows.
   - **Rent payer:** the **outer transaction fee payer** at `init_day_buckets`, recorded in the account as `creator` — **never the vault**. §5.2 rule 4 already forbids vault-funded account creation, and a vault-funded ring would be a rent-drain vector of exactly the kind audited on `revoke_session`.
   - **Close / reclaim:** closed by the root, **or permissionlessly once the account's `generation` has advanced past the recorded one** (every session is invalid by then anyway); rent returns to `creator`. A session revoke **frees and zeroes its row** rather than closing the account.
   - **ABI:** `init_day_buckets` takes exactly `(0) payer` — signer, writable · `(1) smart_account` — writable · `(2) day_buckets` PDA — writable, not a signer · `(3) system_program` — read-only. Every debiting instruction (`transfer`, `execute`, `swap`) takes `day_buckets` as a **named optional account appended after `registry` and before `remaining_accounts`**, writable, PDA-re-derived on use; a `grant_session` that carries per-session day caps while the account is **absent** is rejected.
   - **1B contradicts none of this:** none of it exists in 1B, and 1B keeps rejecting per-session day caps at grant (§4).
5. **Token-2022 — policy splits three ways, not two (rev 8).** "Rejected unless allow-listed" was one bucket where there are three, and it made a permanently unverifiable class look like a future policy toggle.
   - **(i) Deny, never allow-listable — no policy path exists to enable these:** `permanent_delegate` (extension 12) and permissioned-burn behaviour, which are rug-shaped by construction — the mint authority can move or destroy a holder's tokens and no cap the program enforces survives it; and `transfer_hook` (14), which reopens **arbitrary CPI** in the middle of a transfer, can exhaust the depth-4 CPI budget mid-instruction, and defeats the premise that `execute` knows which programs it invoked.
   - **(ii) Allowed, with an inequality instead of an equality:** `transfer_fee` (extension 1). A fee mint makes exact before/after equality false by design, so the check becomes `delta ≥ amount − max_fee` where `max_fee` is read from the mint's `TransferFeeConfig`. Withheld-fee accrual on the mint tail is expected and is not a reject (§5.2 rule 2a).
   - **(iii) Permanent non-goal, out of custody entirely: confidential-transfer mints** (extensions 4/5). Amounts are ZK-hidden, so **conservation is not merely hard to check, it is unverifiable** — the program cannot read the number it would need to bound. This is therefore **not an allow-listable extension and never becomes a policy toggle**: Warden refuses to custody confidential-transfer mints at all, in v1 and after (§13).

   **1B behaviour:** classes (i) and (iii) reject unconditionally; class (ii) rejects too, because the policy allow-list machinery is 1C — 1B's blanket "reject any T22 danger extension" is a *tightening* of this rule, not a different one. The decision is made by inspecting the **mint's** TLV, which is why the mint account must be present (§5.2 rule 2a).
6. **Stage binding**: staged content carries `generation` and `policy_version`; both must equal current at execution; consumed on use.
7. **`swap`** = `execute` specialised: CPI pinned to the Jupiter v6 program id + `route`/`shared_accounts_route` discriminators; source = vault ATA(in_mint), destination = vault ATA(out_mint), `platform_fee_account` = treasury ATA (of in or out mint) else reject; post-state: exactly one vault-owned token account decreases (in_mint, ≤ `max_in` ≤ swap caps), out_mint ATA increases ≥ `min_out`, others unchanged; **`out_mint ∈ allowed_out_mints` for sessions** unless a cap exists for it. Swap input debits the swap buckets (per mint per day, account-wide, rolling 30-day, lifetime per session) **for session and root alike**. *This bounds loss to the swap caps regardless of route quality; it does not check price* — the extension enforces quote sanity (Jupiter quote vs a second price source; > 3% deviation blocks the session path).

### 5.3 What §5.2 does and does not guarantee (§1 boundary)
Guaranteed: bounded token/lamport outflow from **vault-owned token accounts and the PDA's lamports** under session control; no delegate/close-authority/owner change on vault-owned token accounts; no vault-owned token account realloc'd or extension-mutated, and none closed except by the rule-1a vault-sweep exception (direct instruction, zero balance, rent to the PDA). Not guaranteed: semantics inside external programs where the user already holds positions (a session may interact with an allow-listed protocol's position the vault is authority of; e.g. adjust a lending position). Mitigation is the program allowlist + per-op simulation intent; the honest product statement is "bounded loss of what's in your wallet".

**Third boundary: authority that lives inside another program's data (Phase 1B Task 1 round-1 review).** Rule 3 says no vault-owned account type other than a token account may be writable. A snapshot can enforce that only where "vault-owned" is legible from the account header — i.e. `owner_program == the SmartAccount PDA`, and token/mint accounts whose authority fields the program parses. A **stake account, a durable-nonce account, or any protocol's position account whose authority happens to be the PDA** is owned by *that* program and stores its authority inside its own data layout; conservation cannot see it without a parser per program, and one does not exist. Such an account passed writable is therefore **not** caught by §5.2's snapshot. What bounds it is the **Phase 1B Task 3 adapter-registry account-role validators**, which decide per adapter which accounts may occupy which roles, plus rule 1's restriction on which programs a session may CPI at all. This is a *structural* division of labour — the snapshot bounds value, the registry bounds reachability — not a gap scheduled for repair inside the conservation module.

**Second boundary, stated as plainly as the first: the same-CPI round trip (rev 8).** `execute`'s conservation control is a **net** before/after comparison. It therefore measures what an inner instruction *left behind*, not what it *moved*. A single CPI that withdraws 100 SOL of vault value and returns 99.5 SOL within its own execution presents a net delta of 0.5 SOL, and the program bounds 0.5, not 100. **No snapshot granularity closes this** — not per-inner-instruction snapshots, not per-account-write snapshots — because the round trip completes below the boundary at which the caller regains control. This sits beside "cannot verify external program logic" as a **structural limit of the design**, not a defect scheduled for repair. What bounds it in 1B is stated in §5.2 rule 4b: the adapter-decoded `max_in` read from the inner instruction's own data, plus a pinned source ATA, both checked *before* the CPI runs. That is a bound on the value the program can see being *authorised*, and it is the honest answer; it is a design bet, not a proof. The product statement must not claim that a conservation check bounds intra-CPI turnover, because it does not.

### 5.4 Policy lattice (loosening definition, exhaustive)
Fields and their *loosening* direction (must be queued + timelocked; tightening immediate): any cap ↑ (session, swap, ceiling); `large_threshold` ↑; `timelock` ↓; `recovery_delay` ↓; `guardian_threshold` ↓; remove guardian; add allowlisted recipient; add mint to `allowed_out_mints`; add program to any allowlist; **enable a Token-2022 extension — but only from the allow-listable set, which is `transfer_fee` alone (§5.2 rule 5 class ii). `transfer_hook` and `permanent_delegate` are deny-never-allow-listable and confidential-transfer mints are a permanent non-goal (§13): those three are NOT loosening operations, they are absent from the lattice entirely, and `set_policy` must reject an attempt to enable them rather than queue it**; `max_session_life` ↑; `guardian_freeze_max` ↓. Anything not listed is treated as loosening by default. `execute_pending` reclassifies against the policy in force at execution.

### 5.5 Upgrade authority (enforceable)
Devnet: dev multisig. Mainnet: the BPF-loader upgrade authority **is** a Squads multisig (3-of-5) whose proposals carry an on-chain **7-day time lock enforced by the multisig program itself** — the loader authority cannot act faster than that. The extension watches the multisig's proposal accounts: a pending upgrade proposal is surfaced in the extension as an **exit window**. There is **no special `exit` instruction and no timelock waiver**: leaving is the ordinary root path — if needed, queue a policy loosening (raise the relevant caps; 12 h) then queue the sweep (12 h) — both bucketed, delayed and cancellable exactly like any other outflow, so a pending upgrade never opens a fast path for a root attacker. This is sufficient because the multisig's 7-day upgrade lock is ≫ 24 h; the extension additionally offers a one-click 'prepare exit' that queues both steps and reminds the user before the upgrade executes. Commit to immutability at v1.x once stable.

## 6. Extension (MV3)

- **Service worker**: keyring, request queue, Wallet Standard handlers, simulation + policy pre-check, Jupiter client, event watcher. MV3 requires a background service worker for all of this anyway — and it is also the only reliable way to learn the extension's own id at runtime (an MV3 extension with no `background` key registers no worker and exposes no id; `chrome://extensions` is unreachable under `--headless=new`, and CDP `Extensions.loadUnpacked` does not exist in current Chrome-for-Testing builds — spike §12.2). **RP ID vs `rpIdHash`, never conflated:** the credential request's `rp.id` is the bare extension id (= `location.hostname`); the value hashed into `authenticatorData[0..32]` is `SHA-256` of the **full origin** `chrome-extension://<id>` (§4). Test harnesses must launch with `headless: false` plus `--headless=new` in `args` — passing `headless: true` alongside `--headless=new` silently loads no extension at all.
- **Provider**: `registerWallet()` exposing `standard:connect/disconnect/events`, `solana:signTransaction`, `solana:signAndSendTransaction`, `solana:signMessage`, `solana:signIn`; legacy `window.solana` shim.
- **Warden Receipt / intent view** (the most important screen): render from the immutable exact-bytes request record in this order: exact origin/account/network → decoded intent → immediate balance/fee/rent changes → continuing authority/delegate/owner/close-authority changes → evidence and on-chain policy → cost/timing/stop path → an effect-specific decision. Keep four independent axes rather than one green “safe” verdict: origin (*associated / unverified / mismatch / reported*), decode (*full / partial / unknown*), simulation (*current / stale / failed / unavailable*), and policy (*within limits / needs passkey + delay / blocked*). Ordinary balance diffs remain legible `ink` text with signs/labels; semantic color is reserved for independently evidenced status marks. Plain-language intent leads, with a raw-instruction disclosure available for verification rather than used as the default view.
- **Third-party simulation and reputation feeds are ADVISORY ONLY and never a signing gate (rev 8).** **On-chain conservation is the verdict.** No transaction is ever permitted *because* a vendor simulator approved it, and none is blocked solely because a vendor flagged it — a vendor verdict changes what the UI *says*, never what the program *allows*. The reason is measured, not theoretical: Blowfish silently missed a `System::assign` while the wallet displayed "Receive 1 SOL", and simulation in general is bypassable by contracts whose behaviour depends on block context. What Warden *does* take from vendors is the coverage its own architecture cannot provide, rendered as advice: **pre-connect dApp reputation and token/domain blocklists** (fork Phantom's blocklist; Phase 2). Local simulation is still cross-checked against the local policy pre-check and **disagreement between the two is surfaced** (§2, lying-RPC row) — that is a warning, not a gate either.
- **dApp transactions — the honest boundary.** Warden advertises the SmartAccount PDA as the account. A dApp-built tx is **rewritten**: fee payer = session key; dApp instructions are wrapped into `execute` (inline if the whole serialized transaction ≤ 1,232 B; else staged in as many `stage_chunk` transactions as needed, then one `execute` — shown as one flow); ALTs preserved. Because the signed bytes change, the following are **unsupported and rejected with a clear message**: transactions with other required signers/partial signatures, durable-nonce transactions, transactions that need the PDA as a *top-level* signer, instructions that inspect the Instructions sysvar for adjacency, and dApps whose target program is not on the session allowlist (offered: root path). `signMessage`/`signIn` are signed by the session key; dApps that verify against the account address (Sign-In-With-Solana) **will fail** — no Solana-native ERC-1271 exists; Warden publishes a measured per-dApp compatibility list (§12.4) and does not claim Phantom parity.
- **Swap**: `/quote?platformFeeBps=FEE_BPS` → `/swap-instructions` → `swap`; `feeAccount` = treasury ATA; quote sanity vs a second source; `FEE_BPS` = 85 (0.85%, Phantom parity — owner decision 2026-08-18); a gasless tier at 150 bps only if gasless swaps are added later.
- **Address book & poison guard (binding 2026-08-19 UI/security erratum):** first-seen provenance records the exact address and source; dust-only senders are flagged and never become trusted merely by appearing in history. A first-time recipient shows the full Base58 address, trusted-source/QR/manual/deep-link provenance, and a character-level comparison against the last genuine address when a lookalike exists. Matching the displayed first/last characters is **not identity verification**—attackers deliberately grind matching ends. If partial-address typing is retained, it is attention friction only and must say “Displayed characters matched. Recipient identity is still unverified”; it cannot produce an `ok` state, lower risk, or release a dust-only block. A dust/lookalike expert override starts a fresh trusted-source entry, shows the full comparison, requires fresh authentication, and remains subject to policy/timelock. High-value or first sends offer a small test send or timelock.
- **Passkeys/PRF**: root ceremony = WebAuthn `get()` with challenge = action transcript hash; PRF (if available) derives the keyring key; otherwise Argon2id password (mandatory fallback — real-device PRF is UNVERIFIED, §4). Root never touches the extension's memory. The extension normalizes the assertion's S value (low-S) before submitting, §4.
- **Root-transaction byte budget (measured, spike §12.2).** A *minimal* two-instruction root-verify transaction — one secp256r1 precompile instruction (182 B of data) plus the root instruction (367 B, mostly `clientDataJSON` 164 B + `authenticatorData` 37 B + origin 51 B + challenge 43 B) — with two accounts, no ALT and **no payload at all** already serializes to **788 B of the 1,232 B limit**. That leaves ≈440 B of headroom. Therefore: **a root instruction must carry ≤ ~400 B of its own payload, or route through the staged path** (`stage_open`/`stage_chunk`/`stage_finalize`, then a root instruction referencing only the Stage hash). Root `execute` on any non-trivial instruction set is a staged action by construction, and `queue`/`grant_session`/`set_policy`/`set_guardians` must keep their borsh argument encodings inside that budget or stage them. This is also why the session-key path exists: routine actions must not pay the assertion's byte cost.

## 7. Recovery flows

1. **Onboarding** creates root passkey + recovery key (shows the 12-word code once, offers file/QR export) and nudges to add guardians (second device via QR = its passkey pubkey; friend; cloud guardian). Recovery-key alone already makes recovery possible; guardians make it robust to losing the code too.
2. **Lost device**: new device → "Recover" → account address → new passkey → guardians (or the recovery key on the new device) propose+approve → 48 h → execute. Old device (if any) sees "recovery in progress" and can cancel or root-freeze.
3. **Stalemate** (attacker holds root, user holds guardians): guardians freeze; nothing moves; documented.

## 17. Assurance — the L0–L9 pipeline (binding process)

This section is **process, and it binds**: a milestone is not done because the code works, it is done when the layer that proves it has run and its evidence is recorded. Layers are ordered by **dependency, not importance** — L0–L3 are prerequisites for the layers that consume them. L9 runs **in parallel with Phase 1B**, not after it. Full derivation and sources: `docs/research/2026-08-18-security-assurance-and-wallet-landscape.md` §1.

**Artefacts (all under `docs/security/`, except where noted):** `INVARIANTS.md` (generated) + `invariants.jsonl` (source of truth) · `PRIOR-ART-FINDINGS.md` · `REVIEW-SCORECARD.jsonl` · `THREATMODEL.md` · the finding schema at `.codex/schemas/warden-findings.json` · plus `programs/warden/tests/sigverify_wiring.rs`, `.github/workflows/ci.yml`, `scripts/review.sh`, `scripts/deploy-gate.sh`, `THIRD_PARTY_NOTICES.md`. The Codex review profile lives at **`$CODEX_HOME/warden-review.config.toml`** (profiles resolve from `$CODEX_HOME/<name>.config.toml`, **not** a repo-local `.codex/profiles/` path).

**Typed findings, and why truth is separate from evidence.** Codex output is **JSON validated against `.codex/schemas/warden-findings.json` by an independent validator**, never prose and never trusted because a flag was passed (`--output-schema` constrains the *final response*, not every JSONL event). Each finding carries `{id, invariant_ids[], truth_status, evidence_type, severity, file, line, prior_art_cited[], reproducer{base_sha, fixed_sha, test_path}, confidence, notes}`.

- **`truth_status` ∈ `POTENTIAL | CONFIRMED | REFUTED`** — the claim's standing.
- **`evidence_type` ∈ `red_test | static_trace | formal_counterexample | config_attestation | primary_source`** — *how* it is known. These are orthogonal axes and must never be collapsed: "no red test ⇒ inconclusive" would discard static traces, supply-chain and dependency-provenance findings, key-management and release-credential failures, upgrade-authority misconfiguration, economic/MEV and liveness attacks, and formal counterexamples — all real, most unreproducible as a LiteSVM test.
- **A reproducer is required only where one is feasible**, and when present it must **FAIL on the vulnerable base SHA and PASS on the fixed SHA** — "fails on HEAD" is the wrong predicate once a fix has landed. Findings without a feasible reproducer route to **human security adjudication** and are recorded with the reason; they are **never auto-downgraded**.

**Human adjudication rules.**
1. A finding raised by **either** model enters the ledger as `POTENTIAL`.
2. **Agreement between models is a confidence signal, not evidence, and never promotes a finding on its own** — two models can be confidently wrong together, which is precisely why prior-art seeding exists. Agreement raises triage priority, nothing more.
3. `CONFIRMED` requires an **evidence artefact of an allowed type** *or* an explicit **human security adjudication**, recorded.
4. **Disagreement escalates to a human and is never auto-dismissed**; the ruling is recorded.
5. **Any diff that moves an accept/reject boundary gets a mandatory second-round confirm.** Precedent: the round-1 fix to the P-256 root check over-corrected and rejected `x = 0` — a valid point — and a *second* Codex round caught it (`4b409f7`).
6. **Silence on a seeded invariant is a FAIL, not a pass.** Every round must name the sibling files carrying cross-cutting invariants (`transcript.rs`, `state/session.rs`, `errors.rs`, `buckets.rs`) plus the ledger entries overlapping the diff — the one false positive in the pilot came from **reviewer scope, not model identity**.
7. **No tool confers a ledger proof status until it has been piloted on this repo.** Fuzzing is bug-finding, not proof: a clean campaign raises an invariant to `test-covered` at best, never to `proven`.
8. **Every review prompt is seeded with `PRIOR-ART-FINDINGS.md`** — the cheapest counter to shared LLM blind spots on Solana-specific classes — and carries a standing checklist item for **dimensional/scaling bugs** (a cbETH/ETH ratio used as if USD-denominated cost Moonwell $1.78M past a human reviewer).

**Invariant `status` (the ledger's own axis, ascending — a single field with these values, never a boolean alongside it):** `unimplemented → llm-asserted → test-covered → mutation-tested → proven → holds`. **`holds`** is one of those values and means the invariant has at least one accepted evidence artefact of an allowed type **and no open contradicting finding** — it is the ledger-side counterpart of a `REFUTED` attack claim, and it is exactly what L3 samples for false negatives.
